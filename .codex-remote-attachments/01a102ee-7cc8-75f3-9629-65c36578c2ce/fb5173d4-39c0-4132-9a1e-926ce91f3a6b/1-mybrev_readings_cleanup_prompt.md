# MyBrev Web — исправление форматирования страницы чтений и нормализация данных

Работаем **ТОЛЬКО с веб-проектом MyBrev**.

Нужно исследовать и исправить несколько связанных проблем на странице литургических чтений.

## Важно

- не делать редизайн страницы;
- не менять общую типографику приложения;
- не переписывать архитектуру без необходимости;
- главную проблему с большими разрывами текста решить **НА УРОВНЕ ДАННЫХ**, а не спрятать CSS-ом;
- сначала исследовать текущую структуру данных, renderer и pipeline импорта, затем делать изменение;
- не предполагать имена коллекций/полей/компонентов — найти реальные в проекте.

Главный regression example:

**Дата: 2026-10-04, воскресенье**

Открыть страницу чтений этого дня.

Особенно внимательно проверить:

1. первое чтение;
2. респонсориальный псалом;
3. автоматически добавляемые служебные формулы после чтений и после Евангелия.

---

# 1. Респонсориальный псалом на странице чтений

Нужно привести отображение псалма к нормальной литургической структуре.

## 1.1. Номер стиха

Каждый номер стиха должен **ВСЕГДА начинаться с новой строки**.

Например, если исходные данные фактически приводят к:

`...яе.12. Яна парасткі...`

это должно отображаться как:

```text
...яе.
12. Яна парасткі...
```

То же относится к:

- `9.`
- `12.`
- `13.`
- `14.`
- любому другому номеру стиха.

Поддержать многозначные номера.

Очень важно: применять это правило именно внутри содержимого **респонсориального псалма**, чтобы случайно не начать переносить любые цифры во всех текстах приложения.

---

## 1.2. Звёздочка `*`

После литургической звёздочки `*` в псалме должен **ВСЕГДА быть перенос строки**.

Если в данных:

```text
...вінаградную лазу, * прагнаў язычнікаў...
```

результат должен быть концептуально:

```text
...вінаградную лазу,*
прагнаў язычнікаў...
```

Но сохрани правильную пунктуацию исходного текста.

Главное правило:

- `*` остаётся в конце предыдущей строки;
- сразу после неё line break;
- пробел после `*` перед новой строкой удалить;
- следующая строка не должна начинаться с пробела.

Не создавать дополнительный пустой абзац — нужен обычный перенос, а не большой vertical gap.

---

## 1.3. Цвет литургических символов

В респонсориальном псалме символы:

- `*`
- `†`

должны отображаться красным цветом / rubric color приложения.

Не записывать CSS/HTML-стили непосредственно в базу данных.

Лучше использовать существующую систему semantic spans / rich text / classes, если она уже есть.

Если `†` уже имеет специальное поведение, сохранить его; задача здесь прежде всего сделать оба символа визуально rubric/red.

Проверить light/dark theme.

---

# 2. Большие разрывы текста в чтениях

Это основная задача.

На **2026-10-04 в первом чтении** сейчас хорошо видна проблема.

Обычный прозаический текст отображается примерно так:

```text
Заспяваю прыяцелю майму

песню сябра майго пра вінаграднік ягоны:

Мой сябра меў вінаграднік

на ўрадлівай гары.

Ён ускапаў яго...
```

Между фрагментами получается почти ещё одна пустая строка.

Это **НЕ желаемое оформление**.

Сначала найди конкретную запись первого чтения `2026-10-04` в базе/исходных данных и выясни **ТОЧНУЮ причину**:

- лишние blank lines;
- отдельные markdown paragraphs;
- `<p>`;
- `<br><br>`;
- импортированные line wraps;
- массив блоков;
- другая структура.

Не угадывай причину.

Посмотри реальные stored data и путь:

```text
source/import
→ storage/database
→ parsing
→ reading renderer
```

---

# 3. Нужен database/data cleanup script

После того как причина установлена, создать отдельный безопасный скрипт, который проходит по всем:

- first readings;
- second readings;
- other readings, если структура их поддерживает;
- Gospel texts;

и ищет аналогичный дефект.

Это не должен быть специальный hardcoded fix для `2026-10-04`.

Нужно найти **общий pattern повреждённых данных**.

---

## 3.1. Важное ограничение

НЕЛЬЗЯ просто сделать что-то вроде:

```js
replace(/\n+/g, ' ')
```

по всем текстам.

В библейских текстах могут законно существовать:

- реальные абзацы;
- поэзия;
- цитаты;
- отдельные строки;
- заголовки;
- специальные liturgical markers;
- другая значимая структура.

Поэтому сначала классифицируй реальную проблему на примере `2026-10-04` и только потом сформулируй безопасное правило нормализации.

Если проблема появилась из-за конкретного importer/parser, исправь также importer, чтобы новые данные больше не записывались в испорченном виде.

---

## 3.2. Требования к cleanup script

Скрипт должен:

1. по умолчанию иметь **DRY RUN**;
2. находить подозрительные записи;
3. показывать:
   - date/id;
   - type: reading/gospel;
   - краткий before;
   - краткий after;
4. считать количество найденных записей;
5. менять данные только при явном `--apply` или аналогичном режиме;
6. быть idempotent:
   повторный запуск после исправления не должен снова менять те же записи;
7. не трогать записи, в которых он не уверен.

Если текущая storage architecture позволяет — выполнять update безопасно / transactionally / batched.

Не добавлять огромную стороннюю библиотеку только ради этой задачи.

---

## 3.3. Особенно важно

Я хочу именно **улучшить stored content**.

Не решать проблему таким способом:

```css
p {
  margin: 0;
}
```

если в базе по-прежнему остаётся испорченная структура.

CSS можно корректировать только если после исправления данных обнаружится отдельная реальная проблема renderer-а.

---

# 4. Служебная вставка после чтения и Евангелия

На странице приложение автоматически добавляет литургическую формулу после чтения и соответствующую формулу после Евангелия.

Найди место, где эти фразы генерируются.

В обеих формулах первое слово `слово/слова` должно начинаться **со строчной буквы**.

Например, если сейчас приложение генерирует:

```text
Слова ...
```

нужно:

```text
слова ...
```

Сохрани всё остальное написание формулы без изменений.

Это исправление относится именно к automatically generated service text.

Не переписывать из-за этого содержимое библейских чтений в базе.

---

# 5. Желательная архитектура

После исследования выбери минимальное решение.

Предпочтительная схема:

```text
DATA:
existing bad content
→ one-time normalization script
→ corrected database

IMPORT:
new content
→ normalization/validation
→ database

RENDER:
already-normalized content
→ semantic rendering
→ verse line breaks + rubric markers
```

Renderer может иметь небольшую defensive normalization для `*`/verse-number formatting в псалмах, но renderer не должен становиться местом, где мы скрываем испорченные reading/gospel data.

Если текущая архитектура проекта предлагает более чистое решение — используй её, но объясни почему.

---

# 6. Regression checks

После реализации обязательно вручную/автоматически проверить следующее.

## 6.1. 2026-10-04 — first reading

Не должно быть огромных вертикальных разрывов между обычными последовательными строками прозы.

Текст должен читаться естественно.

При этом настоящие смысловые абзацы должны сохраниться.

---

## 6.2. Responsorial Psalm

Проверить конкретно фрагменты с:

- `9.`
- `12.`
- `13.`
- `14.`

Каждый номер начинается с новой строки.

После каждого `*` начинается новая строка без leading whitespace.

`*` красная.

`†` красный.

Нет дополнительного пустого абзаца после `*`.

---

## 6.3. Other dates

Проверить несколько других воскресений и будней, чтобы изменение не было заточено под одну дату.

Особенно проверить тексты:

- без `*`;
- с несколькими `*`;
- с `†`;
- с однозначными verse numbers;
- с двузначными verse numbers;
- с настоящими несколькими абзацами.

---

## 6.4. Service text

После обычного чтения первое слово служебной формулы строчное.

После Евангелия — также строчное.

---

# 7. Не делать лишней работы

НЕ:

- редизайнить Reading page;
- менять bottom navigation;
- менять floating controls;
- менять размеры шрифтов;
- менять глобальные spacing tokens;
- проводить общий рефакторинг Liturgia;
- менять другие экраны MyBrev;
- распространять правила переноса цифр из псалма на обычные чтения.

---

# 8. Перед изменением

Сначала коротко зафиксируй в рабочем отчёте:

1. где хранится reading/gospel/psalm content;
2. в каком конкретно виде хранится проблемное первое чтение `2026-10-04`;
3. почему возникают большие gaps;
4. сколько потенциально затронутых записей обнаружил dry-run;
5. какие правила нормализации предлагаешь.

После этого реализуй fix.

Если во время анализа выяснится, что автоматическое исправление части записей неоднозначно, **НЕ применять к ним агрессивную эвристику**. Вынеси их в список для review.

---

# Definition of Done

Задача закончена, когда:

- проблемное первое чтение `2026-10-04` выглядит нормально;
- исправлены аналогичные повреждённые reading/gospel records в базе;
- есть reusable/idempotent normalization script;
- importer не создаёт снова тот же тип дефекта, если причина была в importer;
- verse numbers псалма начинаются с новой строки;
- после `*` всегда line break без пробела;
- `*` и `†` отображаются rubric/red;
- автоматически добавляемое `слово/слова` после чтения и после Евангелия начинается со строчной;
- другие чтения и страницы приложения не получили визуальных регрессий.

В конце дай:

- root cause;
- список изменённых файлов;
- количество data records, найденных и исправленных скриптом;
- какие записи, если такие есть, были оставлены для manual review;
- результаты regression checks.
