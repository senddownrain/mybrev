# Комментарии к общим категориям молитвенника

Проверенные базы — Web `6f4f20a4` и Flutter `97a9121e` на `origin/main`. Этот документ дополняет [контракт дерева категорий](docs/prayer-categories-contract.md). В работе также находятся Web [#320](https://github.com/senddownrain/mybrev/pull/320)–[#325](https://github.com/senddownrain/mybrev/pull/325) и Flutter [#148](https://github.com/senddownrain/ibreviarybyapp/pull/148) для Access Sets V2. При интеграции этой серии проверить перенос полного документа категории и наследование доступа заново.

## Документ категории

Добавляется одно необязательное поле `comment` в общих категориях `prayerCategories/{id}` и `priestProtectedCategories/{id}`. Личные категории, молитвы и их черновики используют свои существующие модели.

Существующий документ:

```json
{
  "id": "sample-leaf", "name": "Прыклад", "parentId": "sample-root",
  "order": 10, "tags": [], "prayerIds": [], "priestOnly": false
}
```

Тот же документ с комментарием:

```json
{
  "id": "sample-leaf", "name": "Прыклад", "parentId": "sample-root",
  "order": 10, "tags": [], "prayerIds": [], "priestOnly": false,
  "comment": {
    "title": "Тлумачэнне",
    "content": "Узор **афармлення**.\n\n> Прыклад цытаты.\n\n:::rubric\nПрыклад рубрыкі.\n:::",
    "sourceId": "ojcha-nash-2022"
  }
}
```

- `id` берётся из имени Firestore-документа и присутствует в экспортных данных. Дочерние категории отличаются обычным `parentId`.
- `content` — строка в существующем формате `mybrev-markdown` версии 1. Поддерживаются абзацы, заголовки, списки, цитаты, выделения, ссылки и блоки `:::rubric`. Разметка использует структурный рендерер с отключённым HTML. При сохранении переводы строк приводятся к LF, остальная разметка и текст сохраняются. Отсутствующий или `null`-комментарий, а также отсутствующий, `null`, нестроковый или пробельный `content` означают отсутствие блока. При очистке редактор удаляет карту из документа. Титул и источник сами по себе блок не создают.
- `title` — необязательная строка простого текста. Пробельный заголовок равнозначен отсутствующему. Заголовок по умолчанию — «Пра гэты раздзел». Каждый новый вход на страницу начинает со свёрнутого блока. Комментарий открывается до подкатегорий и записей. Категория с одним комментарием и её доступные предки участвуют в прежнем дереве. Поиск и избранное продолжают работать по молитвам.
- `sourceId` — необязательный ID из общего библиографического справочника. Web использует `src/data/sourceBibliography.json`, Flutter — `lib/constants/source_bibliography.dart`. Оба содержат `ojcha-nash-2022`, «Малітоўнік «Ойча наш» (Мінск, 2022)». Использовать его после сверки издания с оригиналом. При неизвестном ID читатель показывает комментарий без строки источника. Библиографическая строка отображается при раскрытии.
- Комментарий наследует доступ документа категории и родителей. Web-админка использует `prayerCategoryService.js` → `prayerStorageService.js` → `prayerStoragePlan.mjs`. План атомарно переносит полные документы по существующему `priestAccessPolicy`, включая `effectivePriestOnly`. Правила `firestore.rules` для категорий проверяют права записи и физическое разделение. Дополнительные правила, индексы, разрешения и коллекции не нужны. У категорий нет процесса черновиков. `prayerDrafts` остаётся отдельной закрытой коллекцией, а прямые ссылки `prayerIds` разрешены только для опубликованных молитв. Для комментариев в старых данных с явным `published: false` или статусом `draft`, `pending`, `review`, `rejected` либо `archived` публичный показ запрещён.

## Web, Flutter и выпуск

| Путь | Чтение и совместимость |
| --- | --- |
| Web Hosting | `export-public-prayers-hosting.mjs` использует существующий `buildPublicPrayerCatalog` в `src/utils/publicPrayerCatalog.mjs`. Администратор и разрешённый священнический путь используют документы Firestore и прежние кэши. Для обычного Web комментарии идут в том же `/public-prayers-v1.json` как необязательная верхнеуровневая карта `categoryComments` вида `{ "sample-leaf": { "content": "…" } }`, только для прошедших публичную выборку категорий. Новый валидатор проверяет ID и поля вложенных карт и возвращает комментарий на соответствующем объекте категории. Старый Web валидирует allowlist полей внутри `categories[]` и `prayers[]`, а дополнительные ключи корня игнорирует. Старый файл без карты и старые офлайн-кэши работают у нового Web. |
| Flutter bundle и обновления | `scripts/content/lib/app-content.mjs` и `build-app-bundle.mjs` сериализуют поля документа `prayerCategories` целиком, после существующей фильтрации прав. Хеш документа включает `comment`. `lib/content/content_bundle.dart` распаковывает карты, `content_store.dart` загружает их в Hive, `content_updater.dart` обновляет по опубликованному манифесту. `lib/providers/prayer_categories_provider.dart` получает доступные карты из защищённого или публичного снимка либо Hive и передаёт их в `PrayerMenuCategory.global`. Формат манифеста и bundle остаётся версии 1. Новая модель должна читать карту аккуратно и добавить комментарий как самостоятельный критерий видимости общей категории. |
| Выпущенные клиенты | В старом Flutter `PrayerMenuCategory.global` читает известные ключи, а `buildPrayerCategoryMenu` отсеивает лист без разрешённых молитв. Неизвестная карта совместима при чтении, но на старом Flutter «Пасвячэнне» будет скрыто. Старый Web игнорирует карту Hosting и также скрывает лист в меню. Наличие молитв в других ветках сохраняет старое поведение этих веток. |

1. Выпустить поддержку чтения на Web и Flutter. B проверяет Markdown, источники, Hive и поведение пустого листа на Android и iOS. Проверить fallback со старым bundle. До этого работать на fixtures. Для старых клиентов, которые продолжат использоваться после выпуска, владельцу нужно принять отсутствие «Пасвячэнне» или выбрать доступную ему политику обновления. Временная фиктивная молитва не нужна.
2. Сверить 8 комментариев, 7 подкатегорий и 24 размещения с оригиналом. Согласовать порядок самих записей по разделам до импорта. Подкатегории идут по `order` внутри одного `parentId`. Для новых разделов задать `tags: []`, а `prayerIds` заполнить проверенными ID опубликованных общедоступных записей, включая повторные размещения одного ID в разных подкатегориях. Точный список и порядок хранить в плане импорта. Повторное использование допустимо после проверки текста, рубрик, издания и публичности. Другие ссылки, теги, права и тексты записей не меняются. «Пасвячэнне» получает пустой `prayerIds` и свой комментарий.
3. Порядок массива `prayerIds` сохраняется в текущих документах, но обе реализации выводят записи по избранному и заголовку. Для гарантии редакционного порядка предлагается отдельно согласовать явный opt-in на порядок `prayerIds` для новых категорий, сохранив текущую сортировку остальных. Включённый режим показывал бы перечисленные ID в заданной последовательности, затем остальные разрешённые прямые записи с текущей сортировкой. Глобальная сортировка молитв и избранное сохраняются. До согласования и реализации на обеих платформах точный экранный порядок 24 размещений остаётся условием выпуска раздела. Сериализация комментария от этого решения не зависит.
4. После отдельного одобрения импорта и проверки статусов выполнить Web-экспорт обычным релизным процессом. Для Flutter выполнить `npm run content:manifest` и опубликовать только проверенный `SAFE CONTENT PATCH` с явным `-- --apply`. Если требуется массовое обновление или меняется схема, использовать `npm run content:app-release` с выпуском приложения. Подробнее в [руководстве публикации](docs/app-content-distribution.md).

## Проверки и расход Firebase

- Локальные данные — `backups/firestore-snapshot` в основном checkout от 27.08.2026 не содержит коллекций молитвенника. Резервный `firestore-snapshot-prayers` от 28.08.2026 содержит 85 молитв и не содержит категорий. Потоки и совместимость проверяются по коду двух `main`, версионированному Flutter bundle и синтетическим fixtures. Полнота боевых данных, совпадения записей и издание раздела требуют отдельной редакционной проверки.
- Web — старые категории, отсутствующее/`null`/пустое поле, короткий и длинный Markdown, рубрика и источник, дочерний лист с нулём молитв, возврат на страницу, клавиатура и `aria-expanded`, размеры экрана, темы и читательские настройки. Админка — создание, повторное открытие, правка, очистка, целостность существующих полей и наследование доступа. Публичный экспорт — проверка старого валидатора, допустимых вложенных полей и исключения защищённых и неопубликованных комментариев.
- Flutter — старый bundle с новой моделью, новая карта в старой модели, форматированный текст с источником, видимость пустого листа по прежней навигации, офлайн и обновление версии через Hive, защита закрытых категорий. Тест выпуска — порядок, 24 размещения и отсутствие утечки в bundle, поиск или избранное.
- Аудит и локальные проверки требуют 0 production-чтений и 0 production-записей. На холодном старте Web по-прежнему один запрос к Hosting для каталога и 0 дополнительных Firestore-чтений. Flutter использует прежний bundle/Hive и текущий цикл синхронизации. Публикация Web выполняет те же три существующих запроса коллекций, без роста их числа. При обновлении Flutter новый или изменившийся комментарий требует чтения одного изменённого документа категории в пределах штатной политики манифеста.
