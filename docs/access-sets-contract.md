# Access Sets V2 · архитектурный контракт S0

Предложение для утверждения перед S1. Web, Flutter, Rules и инструменты используют один контракт в текущем Firebase-проекте. Проверки разработки используют локальные Auth и Firestore Emulator, синтетические данные и `demo-*` project ID.

## Данные и полномочия

| Путь | Назначение и доступ |
| --- | --- |
| `prayers/{id}`, `prayerCategories/{id}` | Существующий публичный формат, доступен старым клиентам целиком. Закрытые записи и закрытые поля не попадают в эти документы. |
| `priestAccess/settings`, `priestAccessPublic/help`, `priestDeviceGrants/{uid}`, `priestActivationClaims/{uid}` | Сохраняются действующие поля, правила, код, proof и сессии. Active legacy grant, привязанный к подписанному UID, даёт только `priest`. Legacy claims остаются недоступны для клиентского чтения. |
| `priestProtectedPrayers/{id}`, `priestProtectedCategories/{id}` | Переходное зеркало legacy priest с теми же ID и legacy-схемой. Пользователь с одним лишь V2 grant к этому пути доступа не получает. |
| `accessSetsV2/{setId}` | Справочник с неизменяемым ID, названием и состоянием для администрирования. `priest` зарезервирован. Архивировать набор можно после проверки зависимостей в профилях, контенте и кодах. Первые значения `priest` и `marian`. |
| `accessProfilesV2/{profileId}` | Авторитетный профиль `{status, allowedSets, revision, …}`. `allowedSets` — явный список ID, без ролей или наследования. Управляющий V2 читает и меняет запись. Изменение опасных прав требует предварительного diff с числом затронутых устройств и явного подтверждения. |
| `accessProfilesV2/{profileId}/client/entitlements` | Проекция только `{allowedSets, revision}` для server `get` владельцем действующего V2 grant с тем же `profileId`. Никакого `list` и содержимого справочника. Проекция обновляется в одной операции с профилем и используется для выбора запросов. Правила выдачи сверяют сам административный профиль. |
| `accessCodesV2/{codeId}` | Связь с неизменяемым `profileId`, `codeProof`, `status`, серверные `issuedAt` и `disabledAt`, необязательная метка. Proof видит только специализированный управляющий. Реестр устройств и обычный UI его не получают. |
| `accessDeviceGrantsV2/{uid}` | `{uid, codeId, profileId, status, deviceName, client, platform, label, activatedAt, lastActiveAt, revokedAt}`. Owner может получить свой документ. Управляющий читает реестр. Выдаваемые владельцем изменения ограничены отложенным отзывом и ограниченным по частоте `lastActiveAt`. Записи без proof. |
| `accessActivationClaimsV2/{uid}` | `{uid, codeId, activationProof, createdAt}`. Только create как часть атомарной активации. Любые клиентские get/list/update/delete закрыты, включая управляющего. |
| `protectedPrayers/{id}`, `protectedCategories/{id}` | Канонические закрытые документы. Сохраняют существующий payload для renderer. Дополнительные поля — `accessSchemaVersion: 2`, `accessSets` для собственных ограничений, `effectiveAccessSets` для авторизации, `contentHash` для сверки. Чтение — админ контента или положительное пересечение авторизованных наборов с `effectiveAccessSets`. |
| `priestContentControl/state` | Единый version/lock для связанных писателей. Существующий протокол остаётся обязательным при изменениях публичного, канонического и зеркального контента. |
| `priestContentControl/accessSetsV2` | Отдельный служебный документ режима выдачи: `legacy`, `canonical` или `suspended`. При отсутствии значения действует `legacy`. Только управляющий меняет режим. Клиент читает минимальный режим для выбора транспорта, а Rules сами проверяют режим перед выдачей canonical. Дополнительных полей у legacy `state` не требуется. |

V2-управление получает отдельное разрешение `accessSetsV2: true` в доверенной записи `admins/{uid}`, а `superadmin` сохраняет право управления. Старый флаг `priestAccess` и список legacy-админов сами по себе дополнительных V2 прав не дают. Обычный админ читает защищённый контент по действующей роли для редактора. Изменение области видимости или публикация с новой видимостью требует специализированного полномочия либо согласованного workflow, проверяемого Rules. В явные исключения wildcard входят все пять `access*V2` и две `protected*` коллекции. Для неизвестных путей внутри зарезервированных корней действует запрет.

## Выдача доступа и жизненный цикл

1. Старый экран «Доступ для святароў» остаётся единственной пользовательской точкой входа. Парсер V2 распознаёт структурированный формат отдельно. Для legacy применяются исходные `normalizeCode` и `codeProof`. Код пользователя не выбирает профиль и не даёт права по префиксу.
2. Предлагаемый wire-формат V2 — `PREFIX-YYYYMMDD-CODEID-SECRET`, где `PREFIX` состоит из 3–10 ASCII букв, дата календарная UTC, `CODEID` содержит 16 случайных символов, секрет содержит 24 случайных символа и может отображаться шестью группами по четыре. Для ID и секрета используется тот же 32-символьный алфавит без неоднозначных знаков, что в legacy. Криптографический генератор выдаёт 120 бит секрета отдельно от 80-битного ID. При коллизии ID генератор повторяет выдачу с проверкой create-only. Нормализация V2 допускает внешний ASCII whitespace и ASCII case folding. Canonical proof — SHA-256 от UTF‑8 строки `mybrev/access-code/v2\n` и канонической uppercase формы с одиночными разделителями полей и непрерывным секретом. Представление — lowercase hex. JS и Dart получают один набор синтетических векторов.
3. Активация использует существующий именованный Anonymous Auth Web или Flutter. `WriteBatch` создаёт claim и grant с ID текущего UID. Rules подтверждают совместное создание через `getAfter`, связь UID и code ID, действующий код, связанный профиль, совпадение proof, `request.time`, обязательные поля, типы и ограничения размеров. Authority для `profileId` — запись кода. Дата в печатном коде связана с proof, а серверное время берётся из Firestore. `allowedSets` в claim/grant отсутствует. Повтор после неизвестного результата сначала читает собственный grant с сервера и не переигрывает подтверждённую пару.
4. На устройстве права вычисляются как объединение независимых источников: `{'priest'}` при активном legacy grant и `allowedSets` активного V2 grant с активным профилем. На свежем UID профиль `marian` даёт только `marian`. На уже активированном legacy UID тот же ввод добавляет `marian` и сохраняет `priest`. V2-код не заменяет действующий V2 профиль этого UID и не оживляет отозванный V2 grant. Смена профиля установки и повторная регистрация после индивидуального отзыва остаются отдельным продуктовым решением. Штатная выдача V2 поддерживает один V2 grant на UID.
5. Ротация и отключение кода прекращают будущую активацию с его proof. Выданные grants сохраняются. Отключение профиля прекращает выдачу по нему и сразу закрывает новые серверные чтения всем его grants. Повторное включение профиля восстанавливает доступ active grants с его текущим набором прав. Индивидуально отозванная запись остаётся отозванной. Отзыв одного реестра оставляет право второго. Полное выключение пользователем сразу очищает локальный доступ, отзывает его активные записи в обоих реестрах и сохраняет до подтверждения минимум состояния для повторной доставки, включая UID. Очистка Auth-сессии после подтверждения следует действующему поведению клиента.
6. Код и proof — секреты. Клиенты держат их только в памяти операции, pending записи не включают доступ, очереди offline для регистрации исключены. Состояние, экспорт реестра, логи, ошибки и аналитика не содержат proof, plaintext или закрытые названия. Публичные сборки содержат алгоритмы и синтетические тестовые данные лишь в исходниках тестов, вне release assets.

## Видимость и выдача каталога

- Собственное `accessSets` пусто для публичного объекта. `effectiveAccessSets` выводится из собственного ограничения и всех защищённых ограничений цепочки `parentId`, ручных `prayerIds`, тегов, `categoryId` и `categoryIds`. Каждое ограничение перечисляет альтернативные наборы. Между ограничениями применяется пересечение. Публичные связи не расширяют его. Несвязанный public item остаётся public, а пустое пересечение защищённых ограничений, неизвестный набор, цикл или оборванная ссылка блокируют сохранение. Для старых спорных данных сохраняется закрытая выдача до исправления. Пример: собственное `['priest','marian']` и родитель `['marian']` дают `['marian']`. `['priest']` и `['marian']` дают конфликт.
- Решение о public или protected принимается до записи. Правила не могут обойти весь граф категорий, поэтому доверенная административная операция пересчитывает граф, валидирует источники и атомарно записывает результаты. Rules проверяют поля, доступ писателя, отсутствие V2-ограничений в публичной схеме и версионные/парные инварианты. Импорт и публикация черновиков пользуются общей политикой. Отдельно проверить ссылки из метаданных публичной категории, чтобы они не выдавали ID, title, теги или другие закрытые сведения.
- Серверный `get` по ID использует то же право. План для списка — отдельный ограниченный `array-contains` по каждому реально авторизованному `setId`, пагинация и объединение результатов. Rules вычисляют полномочия из grant и профиля, дополнительно признавая legacy `priest`. S1 обязан подтвердить в эмуляторе, что конкретная форма `array-contains` и правил проходит положительные и отрицательные проверки и не разрешает широкий `list`. Firestore проверяет потенциальный результат запроса. Если массив и Rules нельзя совместить строго, выпуск блокируется до проверки альтернативы: защищённого индекса ID по набору с разрешённым чтением индекса и отдельным авторизованным `get` канонического документа. Тексты остаются в одном каноническом экземпляре. [Firestore Rules и запросы](https://firebase.google.com/docs/firestore/security/rules-query).
- Бюджет на чтения правил — до 10 обращений за одиночную операцию или query, до 20 на атомарный запрос и до 10 на каждую его операцию. Цель для claim/grant до кеширования — до 4 на запись и до 8 на batch: код, профиль, `getAfter` пары и проверка её отсутствия до commit. Для канонического get/query проверить верхнюю границу с проверкой режима, admin, legacy grant, V2 grant и профиля. Измерить бюджет парных контентных записей и `priestContentControl`, включая неуспешные запросы. Предел в 400 операций текущего writer не переносится как гарантированная ёмкость V2. Пагинация и пределы профиля фиксируются в S1 после измерения квоты и Rules. [Лимиты Rules](https://firebase.google.com/docs/firestore/security/rules-structure).
- Web и Flutter читают закрытое только с сервера через отдельную Firestore без дискового кеша. Смена сессии, отзыв, изменение профиля, потеря текущей серверной проверки, offline и уход в фон очищают reader, поиск, результаты и миниатюры в памяти, а поздний ответ отбрасывается по поколению. Для обновлений профиля S1/S2 проверяют доставку invalidation (включая отказ server stream), foreground/reconnect и ограниченное повторное подтверждение для открытого reader. Избранное хранит ID, его карточка строится только из разрешённого каталога.

## Зеркало, идентичность и выпуск

- Copy migration переносит закрытые priest записи по исходному ID и без изменения байтов текста/вариантов, markdown, рубрик, тегов, связей, source или собственных legacy-флагов. Эффективное право копии — `['priest']`. Если собственный `priestOnly` был false, значение сохраняется и вычисленное ограничение остаётся priest. Изменения layout и прав хранятся отдельными полями V2.
- Зеркалируются документы с итоговым набором ровно `['priest']`. Канонические записи, которые также доступны новому набору, выдаются новым клиентам из canonical и не попадают в зеркало. На первоначальном переходе прежнюю зеркалируемую запись нельзя переопределить в публичную или смешанную. Превращение ранее публичной записи в закрытую также требует отдельного решения: существующие APK/IPA, Hosting, кеши и уже скачанные копии могут продолжать раскрывать старый текст.
- Гарантия пары — одна атомарная операция canonical + legacy + обновление version, с проверкой readback. SHA‑256 считают по стабильной, типосохраняющей сериализации общего payload со сравнимыми Firestore timestamp/reference/bytes и ключами в фиксированном порядке. Из сравниваемого canonical payload исключаются только V2-поля контракта. Hash сверяет целостность, авторизация сверяет `effectiveAccessSets`. `getAfter` и проверки парного payload в Rules проходят в S1/S4. Если изменение не помещается в write, byte или Rules limits, админская выдача отказывает и передаёт операцию проверенному плану с блокировкой.
- На время начального копирования админ-писатели заморожены. До полного readback режим `legacy` закрывает canonical для пользовательской выдачи и разрешает новому клиенту прежний источник только при подтверждённом legacy grant. В режиме `canonical` парность поддерживают Rules и writer, а отдельная сверка проверяет записи из доверенных инструментов, обходящих Rules. Reader убирает дубликаты по `(тип, ID)` и скрывает замеченные public/private коллизии или неполный результат. Устройство с одним V2 grant не читает зеркало для проверки. Если сверка обнаружила расхождение, оператор переводит canonical в `suspended` до восстановления. Вернуть `legacy` для новых клиентов можно после подтверждения целостности зеркала. Старому клиенту доступен его исходный путь.
- Закрытые payload, previews, метаданные и индексы не входят в Hosting JSON, Flutter bundle/manifest, Service Worker Cache, IndexedDB/Hive, APK/IPA или публичные экспорты. Контроль одинаков на прямых ссылках, в поиске, категориях и избранном. При затрагивании публичных коллекций применяется текущая явная процедура публикации manifest.
