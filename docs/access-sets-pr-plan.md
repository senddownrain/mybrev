# Access Sets V2 · план отдельных PR

S0, исправление тестов, release gate и фундамент S1 подготовлены в отдельных Draft PR. Последующие этапы ниже описывают объём будущих PR. Исходная база и ограничения приведены в [аудите](access-sets-audit.md), критерии поведения — в [контракте](access-sets-contract.md) и [матрице совместимости](access-sets-compatibility.md).

Разработка ведётся в отдельных ветках и проверяется локально на Auth + Firestore Emulator. До разрешения владельца PR остаются без merge там, где merge может опубликовать Web. Служебный PR по блокировке релиза согласуется первым, поскольку текущий Web workflow сам включён в push path filters. Условие безопасного merge для остальных PR — проверенный контроль production jobs, включая параллельные Hosting workflow, и отсутствие автоматического production dispatch. Проверка S1 выявила, что окружение `production` пока не требует независимого GitHub reviewer. Перед первым выпуском V2 настройку принимает владелец.

## Критерии первого PR по Rules

- Положительные сценарии сверяют новый активный grant, старый grant после ротации, `priest`, `marian`, профиль с двумя наборами и обычного администратора контента. Негативные утверждения покрывают отсутствие права, отозванный grant, выключенный профиль, незарегистрированный набор, чужой UID, лишние поля, даты, неправильный proof, попытку одиночного claim/grant, прямое чтение служебного пути и широкий запрос. Используются синтетические учётные записи и фикстуры.
- Проверить создание и обновление там, где есть оба разрешения, `get/list` и вложенные пути. Владелец не правит профиль, код, proof, чужой grant или статус revoked обратно в active. Включить в отчёт количество Rules access calls и batch с максимально поддерживаемым числом операций без допущения о cache hits.
- Зафиксировать сценарий частичной availability после выключения только одной ветки прав. Правила убирают серверный доступ, Web и Flutter отбрасывают ранее запущенные чтения и очищают экран после invalidation. Для полного выключения flush происходит до завершения Auth-сессии.
- Для `array-contains` тестировать запросы, которые реально будут использовать Web и Dart SDK, включая фильтр, лимит и курсор. Отдельно проверить, что `get` проверяет ту же область, которую допускает каталог. При невозможности доказать строгую выдачу оставить путь закрытым до согласования альтернативы.
- В описании PR — SHA базы, изменённые файлы, локальные команды, PASS/FAIL/SKIP, остаточные ограничения, данные, которые потребуют отдельной production проверки, и вариант отката. Никаких закрытых payload, реальных UID, proof или кодов в logs/artifacts.

## Порядок ручного релиза

1. Проверить актуальные Rules, наблюдаемую квоту, снимок, активные legacy clients и согласованную матрицу. Назначить владельца проверок каждого канала и собрать точные входные версии/артефакты.
2. Опубликовать совместимые Rules с закрытым маршрутом для непроверенного каталога. Пройти smoke legacy public/grant/reader. Получить разрешение на copy, выполнить backup → dry-run → copy → readback и включить dual-write после проверки версии. Оставить старые документы, связи, коды и grants.
3. Разрешить подключение Web V2, проверить старый PWA и новый Web, затем Android и iOS. Проверить ранее активированный UID без повтора кода, новый legacy `priest`, отдельный V2 `marian`, явный смешанный профиль, ротацию, отзыв, offline/reconnect и старые APK/IPA. При сбое применять [матрицу отката](access-sets-compatibility.md#откат-и-удаление-моста).
4. При изменении `prayers` или `prayerCategories` отдельно прогнать отчёт `npm run content:manifest`. Только согласованный SAFE CONTENT PATCH допускает `-- --apply`, а массовое или схемное изменение потребует app release по регламенту. Закрытый импорт сам по себе в публичный manifest не входит. [Дистрибуция приложения](app-content-distribution.md).
