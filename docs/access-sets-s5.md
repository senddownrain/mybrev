# Access Sets V2 · Copy Migration S5

S5 опирается на [контракт S1](access-sets-contract.md) и [writer S4](access-sets-s4.md). База разработки — [Draft PR #323](https://github.com/senddownrain/mybrev/pull/323) на SHA 8f8c33c07fbbf3e0f69d167f0494e6cf133a57f4.

## Что переносится

Каждый документ priestProtectedPrayers и priestProtectedCategories получает пару из канонической копии с прежним ID и пустого ID-индекса в наборе priest. Копия сохраняет каждое поле legacy payload и добавляет accessSchemaVersion, accessSets, effectiveAccessSets и contentHash. У каждой копии accessSets и effectiveAccessSets равны ['priest']. Хеш вычисляется функцией S4. После формирования плана проверка S4 валидирует также зависимости категорий, отсутствие публичных дублей и точный состав индексов.

Совпадающие с планом документы на стороне назначения сохраняются с исходными метаданными. План может достроить отсутствующую половину такой пары. Конфликтующий payload, посторонний индекс и неполный граф останавливают миграцию. S5 пишет только недостающие канонические копии, ID-индексы и служебный журнал в зарезервированном пространстве priestContentControl. Legacy и auth-коллекции, версия контента, режим rollout и реестр наборов сохраняются.

## Резервная копия и локальный план

backup фиксирует единый серверный readTime, проект и database ID, пути, поля Firestore Value, createTime и updateTime. Охват включает оба публичных каталога для парности, два legacy-зеркала, два канонических каталога, accessSetsV2, ID-индексы всех обнаруженных наборов и две записи контроля контента и rollout. Пустые коллекции записываются явно. Поиск отсутствующих родительских документов обнаруживает индексы под удалённым набором. Изначально журнал и его операции должны отсутствовать. Auth-данные не входят в область чтения и резервирования. [Firestore ListDocuments](https://docs.cloud.google.com/firestore/docs/reference/rpc/google.firestore.v1#listdocumentsrequest)

Инструмент читает и записывает через Firestore gRPC. Типизированный снимок сохраняет разницу между int64 и double, микросекундные timestamps, bytes, геоточки, ссылки, векторы и вложенные поля. Отдельный SHA-256 связывает поля и метаданные снимка. Команда plan читает только этот файл, проверяет полноту и выдаёт digest плана, digest итогового корпуса и число записей. Один файл на одной версии инструмента даёт один и тот же результат. Снимок общего формата db:snapshot:query полезен для анализа охвата, а для S5 требуется специальный типизированный backup.

Локальные артефакты помещаются непосредственно в игнорируемый каталог backups текущего worktree. Для рабочего снимка заранее ограничьте ACL каталога операторами, храните резервную копию и её SHA-256 в утверждённом зашифрованном хранилище. Реальные снимки остаются вне Git, CI и публичной статики. Сохраняйте агрегированные результаты команд и SHA-256 отдельно от закрытого снимка.

## Репетиция

Нужны npm ci, Firebase CLI и Java 21 для текущего Firestore Emulator. Команда npm run test:access-sets-v2-copy поднимает Firestore Emulator в demo-access-s5. Она создаёт синтетические данные, проверяет copy и readback, прерывает apply и restore после коммита и продолжает их с тем же снимком. Дополнительно проверяются несовпадения, серверный отказ транзакции и неполные данные.

## Разрешения перед production

1. Зафиксируйте проверенный SHA S5 и точные Firebase project/database. Убедитесь, что S1 Rules уже действуют в целевой среде и защищают канонический корпус, индексы и журнал. Сохраните доказательство проверки Rules. Публикация Rules, Hosting и переключение canonical требуют отдельных релизных операций.
2. Повторите репетицию copy, verify, прерывания, resume и restore на той же версии инструмента. Назначьте оператора с утверждённой учётной записью ADC и минимально необходимым Firestore IAM.
3. Сначала проверьте локальный backups/firestore-snapshot/manifest.json через штатный loader или db:snapshot:query. Подтвердите окно, квоту и бюджет чтений/записей для backup, apply, verify, возможного resume и restore. Для каждого полного скана учитывайте все документы указанных коллекций, чтения пустых коллекций, реестр с отсутствующими родителями и журнал. Один шаг копирования записывает 3–4 документа, включая курсор и квитанцию. Один шаг восстановления удаляет 1–2 копии и записывает курсор. Для запуска после сбоя заложите полные повторные сканы и чтения транзакций.
4. Подтвердите freeze на всё окно. Остановите легаси-редакторы и импортёры, S4 writer и любые SDK/Admin-задачи, которые меняют сканируемые документы, настройки rollout или реестр. Оставьте текущий пользовательский режим. S5 принимает отсутствующий rollout, legacy или suspended, требует разблокированный корректный priestContentControl/state и существующий корректный активный accessSetsV2/priest. Для устойчивости между общими сканами нужен операционный freeze. Транзакции дополнительно защищают режим, состояние контента, priest set, исходник текущей операции, её цели и курсор.
5. Получите отдельное разрешение владельца на production backup после проверки квоты. Запишите подтверждение в change record. Для команды подготовьте приватный JSON с action равным backup, полным database вида projects/PROJECT/databases/DATABASE, planDigest равным null, идентификатором change и approvedBy. При работе с production переменная FIRESTORE_EMULATOR_HOST должна отсутствовать.
6. Снимите backup и запустите offline plan. Проверьте полный охват, ожидаемые числа, SHA-256, отсутствие конфликтов и парность S4. Сохраните закрытый backup и результаты dry-run. После этого получите **отдельное разрешение владельца на копирование** с указанием project/database, SHA кода, backupDigest, planDigest, ожидаемых чисел и окна. Для запуска подготовьте новый approval JSON с action равным apply и утверждённым planDigest. Файл фиксирует внешнее разрешение, а IAM проверяет право на доступ.
7. Получите отдельное разрешение на readback verify и держите возможность отдельно утвердить restore. JSON для каждого действия указывает свой action и тот же planDigest. Разрешение на resume должно покрывать тот же план, действие и активное окно. По истечении окна согласуйте продолжение. Переход к canonical и марианский импорт требуют собственных решений.

## Команды для утверждённого окна

Ниже PROJECT, DATABASE и PLAN_SHA заменяются точными утверждёнными значениями. Подставьте соответствующие приватные файлы согласований. Для операционного выполнения используйте worktree с проверенным SHA.

    npm run db:access-sets-v2-copy -- backup --snapshot backups/s5-copy.json --project PROJECT --database DATABASE --production-approval BACKUP_APPROVAL
    npm run db:access-sets-v2-copy -- plan --snapshot backups/s5-copy.json
    npm run db:access-sets-v2-copy -- apply --snapshot backups/s5-copy.json --project PROJECT --database DATABASE --approve-digest PLAN_SHA --production-approval APPLY_APPROVAL
    npm run db:access-sets-v2-copy -- verify --snapshot backups/s5-copy.json --project PROJECT --database DATABASE --production-approval VERIFY_APPROVAL

На apply Firestore атомарно создаёт недостающие документы пары, квитанцию и обновляет курсор. Квитанция связывает операцию с планом, а метаданные коммита различают исходные цели и документы, созданные этим запуском. После последнего шага полный readback проверяет точное совпадение с планом и метаданные baseline. Только после этого журнал фиксирует verified. Отдельный verify повторяет readback. Сохраните согласования и результаты. После verified и независимого readback можно завершить freeze по решению владельца. Если редактирование продолжается, для последующего cutover необходима новая сверка перед открытием canonical.

## Прерывание и восстановление

При истёкшем времени запроса, ошибке транспорта или остановке процесса сохраните freeze, исходный снимок и согласования. При действующем разрешении повторите ту же команду apply с тем же digest. Она проверит прогресс по Firestore и продолжит с первого незавершённого шага. Запуск с confirmed verified повторит полный readback без записи.

При решении об откате получите отдельное разрешение restore для этого planDigest:

    npm run db:access-sets-v2-copy -- restore --snapshot backups/s5-copy.json --project PROJECT --database DATABASE --approve-digest PLAN_SHA --production-approval RESTORE_APPROVAL

Restore проверяет исходный снимок и квитанции, откатывает завершённые шаги в обратном порядке и удаляет только принадлежащие этому запуску копии и индексы. Все записи одного шага имеют общий момент коммита. [Изоляция транзакций Firestore](https://docs.cloud.google.com/firestore/native/docs/transaction-data-contention#serializable_isolation_by_commit_time) Совпадающие документы, существовавшие до запуска, сохраняются с прежними createTime и updateTime. Повтор той же команды продолжает прерванный restore. Итоговый verified readback после restore проверяет baseline, а журнал сохраняет терминальный результат restored для аудита.

При drift, конфликте журнала или неожиданном изменении прав остановите операции и сохраните закрытые снимки, журнал и агрегированный код ошибки. Держите canonical закрытым. Владелец согласует отдельную сверку и адресный план восстановления по сохранённому preimage, текущим версиям и квитанциям. Firestore назначает createTime и updateTime сам, поэтому восстановление потерянного документа из preimage возвращает поля, а исходные метаданные остаются доказательством в снимке. Терминальный журнал не сбрасывается командой S5. Для нового запуска после restore требуется отдельное операционное решение по архивированию журнала и новый backup/dry-run.

Публикация app content manifest для S5 не требуется, поскольку его входные коллекции не изменяются.
