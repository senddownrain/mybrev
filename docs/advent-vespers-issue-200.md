`19125bb81dd07f233ca404ce8b2473dbcbd612b6`, `assets/content/days.json.gz`:

страницами и текущими production-документами не заявляется выполненной.

## Диагноз и окончательный выбор источников

Отдельных полей `НРП` и рэспансорыя в схеме нет. НРП — литургическая
категория собственных текстов; короткое чтение **и весь рэспансорый** хранятся
одним HTML-блоком в `vesperR`.

| Вечер / поля | До исправления | После исправления |
|---|---|---|
| 19.12.2026, I Нешпары: Hymn, Ant1–3, Ps1–3, R, Inter, Pr | Завтрашний `advent-20-12`; отсутствующие `vesper1*` подменялись обычными вечерними полями даты | `advent-w4-d1.vesper1*` |
| 20.12.2026, II Нешпары: те же поля | `advent-20-12.vesper*` перекрывал воскресный Office | `advent-w4-d1.vesper*` |
| O-антифон, 19 / 20 декабря | Мог переходить на завтрашнюю дату в I Нешпарах | `advent-19-12.vesperAntMag` / `advent-20-12.vesperAntMag` |
| 21.12, `vesperR` | В самом `advent-21-12` записан воскресный 1 Фес 5, 23–24 с другим рэспансорыем | Собственный 1 Кор 4, 5 + рэспансорый; дословно из эквивалентного `advent-w2-d4.vesperR` |
| 21.12, `vesperInter` | Воскресные просьбы в датированном документе | Собственные просьбы 21 декабря; эквивалентный текст `advent-w2-d4.vesperInter` |
| 21.12, `vesperPr` | Воскресная молитва в датированном документе | Явное `advent-21-12.vesperPr` с проверенной молитвой даты; существующий текст совпадает с `laudesPr` |
| 23.12, `vesperPs1/2/3` | В бандле датированные псалмы отсутствуют; фактический плохой источник — `advent-w4-d4`, содержащий рождественские I Нешпары | `ordinary-w4-d4`: среда IV недели псалтыря, Пс 139 (138) I/II, Клс 1, 12–20 |
| 23.12, антифоны и другие proper-поля | Датированные тексты | Сохранены; псалмы меняются независимо от антифонов |

`resolveAdventDateAgainstPeriod` задаёт приоритет **по полям**. Воскресный
Office берётся из текущего воскресенья; специальные Benedictus/Magnificat
антифоны остаются датированными. Будни сохраняют собственные тексты даты,
а вечерние псалмы берутся из действующего слота четырёхнедельного псалтыря.
Непустые псалмы, материализованные в календарную дату или сезонный документ
из другого исходного года, не меняют это правило. Другие часы будней не
пересобираются по новому правилу псалмодии.

Для старого бандла предусмотрен точечный переходный слой: он заменяет
только записанные старые значения 13 проверенных полей. Будущие редакторские
изменения сохраняются. Аудит при этом сравнивает проблемные proper-поля с
проверенным формуляром и не объявляет произвольный новый текст правильным
лишь из-за канонического ID документа.

`vesperPr` 21 декабря после сборки заполнено явно; компонент не использует
его общий fallback к `laudesPr`. Копирование одинаковой молитвы при подготовке
proper-поля — проверенное исправление данных, не fallback во время показа.
Новый `CONTENT_REVISION` заставляет обновить ранее собранный кеш.

## Точечный dry-run Firestore

Команда работает только офлайн, не импортирует Firebase SDK и отвергает
`--apply`:

```sh
node scripts/liturgy/plan-advent-vespers.mjs \
  --snapshot backups/flutter-bundle-issue-200 \
  --out backups/advent-vespers-dry-run
```

Получено: **2 документа, 13 полей, 0 конфликтов, 0 записей**.

| Документ | Изменяемые поля |
|---|---|
| `days/advent-21-12` | `vesperR`, `vesperInter`, `vesperPr` |
| `days/advent-w4-d1` | `vesper1Hymn`, `vesper1Ant1`, `vesper1Ant2`, `vesper1Ant3`, `vesper1Ps1`, `vesper1Ps2`, `vesper1Ps3`, `vesper1R`, `vesper1Inter`, `vesper1Pr` |

Полные before/after доступны в проверяемом JSON выше. `vesper1AntMag`
не материализуется: он зависит от гражданской даты вечера. Документ
`advent-23-12` не меняется; ошибка выбора псалтыря исправлена в резолвере.

Приватные артефакты: `backups/advent-vespers-dry-run/backup.json`,
`plan.json`, `summary.md`. Резервная копия содержит оба исходных документа
целиком и SHA-256; если входной снимок имеет `updateTime`, оно сохраняется.
В бандле production `updateTime` отсутствует, поэтому **productionReady=false**.
Это резервная копия офлайн-источника, не обещание актуального backup production.

Перед отдельным разрешённым применением нужны свежие backup/updateTime ровно
двух документов, сверка хешей/старых значений и атомарные field-level updates
с `lastUpdateTime`. Любое расхождение прерывает весь патч. После readback и
аудита отдельно проверяется публикация content manifest согласно
[app-content-distribution.md](app-content-distribution.md). Ни запись в базу,
ни публикация manifest, ни merge/deploy здесь не выполнялись.
