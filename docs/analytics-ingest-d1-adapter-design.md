## 2. Модель D1, которую нельзя предполагать
- В Workers **нельзя** считать, что `BEGIN IMMEDIATE` из прототипа переносим: по документации D1 работает в auto-commit, транзакция задаётся через `D1Database.batch()` («batched statements are SQL transactions»: при сбое одного — `aborts or rolls back the entire sequence`; выполняются последовательно, не параллельно). Про ручные `BEGIN/COMMIT` в Worker API документация молчит ⇒ **не использовать**.
- `Map` в памяти изолята (`storage-memory.mjs`) — только модель для тестов: изолятов может быть много, состояние не общее и теряется.
- `batch()` **не позволяет ветвиться по результату предыдущего оператора**. Поэтому схема «прочитать → решить → записать» в D1 невозможна; решение должно быть выражено в самих операторах.

## 3. Предлагаемый дизайн (гипотеза для проверки)
Миграция `0002` (НЕ создана в этой ветке, только описание): `daily_budget(day PK, rows_written INTEGER NOT NULL, cap INTEGER NOT NULL, CHECK (rows_written >= 0 AND rows_written <= cap))`.

Один вызов на пакет, один `batch([...])`:
1. `INSERT INTO daily_budget(day, rows_written, cap) VALUES(?1, ?2, ?3) ON CONFLICT(day) DO UPDATE SET rows_written = rows_written + excluded.rows_written` — при превышении `cap` нарушается CHECK ⇒ оператор падает ⇒ **весь batch откатывается** (ни одной ячейки);
2. N операторов `INSERT INTO cell_counts … ON CONFLICT DO UPDATE SET n = n + excluded.n` (или многострочные, ≤ 100 привязанных параметров на запрос ⇒ ≤ 50 ячеек на оператор; предел проверить).
Ответ клиенту: 204 при успехе, 503 при любой ошибке batch (клиент, по протоколу §5, пакет не повторяет). Тест на SQLite-движке доказывает работоспособность идеи «CHECK ⇒ откат всех операторов» (`p06-sqlite.test.mjs`, тест CHECK-abort), но **не** доказывает поведение D1.

Открытые вопросы, отмеченные NOT VERIFIED: (a) действительно ли упавший оператор batch откатывает ранее выполненные операторы того же batch в D1 именно так; (b) лимиты на число операторов в batch и привязанных параметров (пакет до 200 ячеек = 201 оператор); (c) считается ли batch одним subrequest/запросом на Workers Free (лимит 50); (d) CPU-лимит Free 10 мс на запрос при 200 upsert; (e) сериализация записей к одной БД под конкурентными вызовами (ожидается, но не проверено); (f) идёт ли ответ клиенту до фиксации.

## 4. Стоимость — допущения, а не факты
Документация считает записанные строки по INSERT/UPDATE/DELETE, индексы добавляют записи, про UPSERT явно не сказано. Принято (НЕ доказано биллингом): upsert = 1 строка; строка бюджета = +1 за пакет; удаление retention тоже тратит записи (≈ число удалённых строк). Сверить на тестовом аккаунте через `meta.rows_written` (§7). Стоп на 80 % — защита от остановки Free-лимита, а не гарантия счёта.

## 5. Идемпотентность: что можно и нельзя
**Теорема (тест «idempotency»):** без идентификатора пакета сервер не отличает «запрос не дошёл» от «дошёл, ответ потерян». Клиент в обоих случаях видит timeout, а состояние сервера различается ⇒ любая политика повтора либо недосчитывает (at-most-once), либо задваивает (at-least-once). Exactly-once невозможно без токена.

**Рекомендуемый протокол (без новых идентификаторов, схема v2 не меняется):**
1. Агрегаты накапливаются локально по UTC-дню (как сейчас).
2. Перед отправкой клиент **атомарно вырезает** отправляемую дельту из буфера (mark-before-send), затем делает один `POST`.
3. Любой исход, кроме 204, включая timeout, 5xx, сбой приложения во время отправки: **дельта не возвращается и не повторяется**. Не повторять автоматически, не ставить в очередь повторов.
4. Не раньше следующего окна отправки (≥ N часов) и только по согласию/kill switch (P07).
Эффект: систематический **недосчёт** на долю потерянных запросов (значение неизвестно; измерять на синтетическом mock-транспорте P07). Дубликаты возможны только от посредников (HTTP-стек/прокси, повторяющие POST после разрыва соединения): величина неизвестна, `NOT VERIFIED`.

**Альтернативы (решает владелец, G11):** (2) случайный токен на пакет + таблица токенов на 48 ч на сервере: защищает от повторов, но это идентификатор пакета, +1 запись строки на пакет, нужен TTL-чистильщик; (3) дедупликация по хэшу тела: **опасна** — одинаковые мелкие пакеты разных людей (одно открытие «Песни») идентичны, будет массовый недосчёт; (4) подписанные токены/attestation: секреты в приложении, противоречит ограничениям. Device/session/user ID и скрытые отпечатки не добавляются ни в одном варианте.

## 6. Малые ячейки (k = 5) и редкие открытия
`k` — **проектный порог показа, не анонимизация входящих пакетов**: сервер видит каждый пакет (и периметр — IP/время). `buildReport`: каждая публикуемая величина — функция только ячеек с `n ≥ k`; итоги — суммы показанных ячеек (нижняя граница, флаг `totalsAreLowerBounds`); число скрытых ячеек не публикуется; тест неинтерференции (200 раундов) показывает, что исчезновение/изменение любой скрытой ячейки не меняет ни байта вывода ⇒ скрытую ячейку нельзя восстановить через итоги, разности или срезы **этого** отчёта. Единичное открытие редкого религиозного материала (n = 1…4) не показывается, не логируется (логи — только фиксированные коды, тест с «sentinel»).
**Остаточные риски (не закрыты):** (1) накрутка: поддельные пакеты позволяют подтолкнуть скрытую ячейку через порог и узнать по разности, что реальные открытия есть (защиты без аутентификации нет; ограничивают лишь потолки `n`, число ячеек и бюджет); (2) порог на уровне суток: пересечение нескольких опубликованных отчётов за разные группировки допустимо только при тех же правилах (всё — функции показанных ячеек); (3) любое добавление «процентов», «доли» или «уникальных» значений требует нового анализа; (4) читающий контур (авторизованное чтение) не существует — тесты проверяют, что ядро не экспортирует чтение и `GET` → 405.
