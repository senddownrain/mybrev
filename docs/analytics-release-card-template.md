# Release-card: ограниченный выпуск аналитики и откат (шаблон)

Шаблон: `07_RELEASE_CARD_AND_ROLLBACK.md`. Заполняет **уполномоченный человек, ответственный за публикацию** (разработчик, если ему делегированы полномочия; иначе назначенный ответственный). **Claude не квалифицирует юридическую допустимость и не доказывает правомерность обработки.** Отсутствие галочки в интерфейсе (решение владельца) само по себе не подтверждает соответствие правилам платформ и регионов.

Текущее состояние на 2026-10-27: **ни одно поле ниже не подтверждено → `LIVE_REPORTING` не объявляется, реальный сбор OFF.** Инженерный статус — `STAGING_BLOCKED_BY_ACCESS` (`docs/analytics-week-closeout.md`).

## Правило остановки

Если любое обязательное поле пусто, `TBD` или не подтверждено ссылкой — **не включать сбор у реальных пользователей** и не направлять их пакеты в какой-либо endpoint. Готовность инженерии (staging, панель, тесты) этому не мешает и этого не заменяет.

## Порядок после подтверждения всех полей

1. **Controlled synthetic canary** на том же конфиге, что предлагается для live: проверить схему, лимиты, доступ, платформы (повторить `docs/analytics-week-closeout.md` §7 против целевого хоста).
2. **Отдельный live-ingest** с собственным D1 и Access. Не использовать staging с тестовыми пакетами как production-статистику — показатели будут загрязнены синтетикой.
3. **Ограниченный rollout** только на одобренные и раскрытые платформы/версии: WEB отдельно; Android — через разрешённую дорожку тестирования/релиза; iOS — через свой процесс. Не обходить проверки App Store / Google Play.
4. Первое окно данных на агрегированном уровне: usage D1, отсутствие личных полей, отсутствие синтетики в live. Панель должна явно показывать `LIVE` и период (режим `live` в панели включается только при `LIVE_RELEASE_CARD`, иначе 503 `mode_not_cleared`). Скрытых профилей не создавать.
5. Алерты (порог — TBD ответственным): рост ошибок схемы, бюджета/стоимости, неавторизованный доступ, payload в логе, неожиданные события, нарушение disabled-режима. При тревоге: `INGEST_ENABLED=false` на сервере **и** выключение на клиентах (сборка без флагов), затем разбор.
6. Простой план отката к предыдущему стабильному build; повтор потерянных пакетов не делается.

## Если подтверждены не все поля (в том числе на седьмой день)

Итог честно называется `STAGING_OPERATIONAL / PRODUCTION_READY_BEHIND_RELEASE_GATE` (если staging реально работает) или `STAGING_BLOCKED_BY_ACCESS` (как сейчас). Передать: готовую приватную панель на тестовых данных, команды включения и выключения, эту карточку и список неподтверждённых полей. Ничего не скрывать от ревью магазинов и не обходить их проверку.
