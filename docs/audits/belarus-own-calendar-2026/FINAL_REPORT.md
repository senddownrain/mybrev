## 3. Что реально находится в Firestore

Проект **ibreviaryby** подтверждён конфигурацией и переменной окружения. Начальное и конечное чтение `liturgicalCalendarMeta/current`: schema 1, revision **3**, notesRevision **4**, publishedAt **2026-10-07T18:15:01.305Z**; updateTime в bookends совпал. Production содержит **241 celebration,75 diocese override,15 year override**. Notes COUNT=**1337**; их тела не читались, потому текущий Web имеет bundled notes revision**6**,1347 заметок и отвергает older revision4.

Все 316 постоянных документов совпадают с Web по календарным полям; server добавляет `importedAt`. Это проверено сравнением каждого ID/canonical hash и локальными resolved-day результатами. Четыре year override совпадают по поведению после legacy normalization; ещё 11 actual auto-transfer документов повторяют computed rules. Не следует объявлять 11 лишних year документов 11 новыми праздниками.

Всего **6 HTTP запросов**, без retry: два masked meta GET, три collection list GET, один read-only COUNT POST. Получено 333 document payloads,332 уникальных документа; COUNT не выгружал 1337body. Это не точный Firebase billing-счёт. Другие коллекции не сканировались. Приватный snapshot, credentials и пользовательские данные не включены в ветку; в final-evidence только необходимые метаданные, IDs, хеши и локальные результаты. ## 4. Что реально использует Web

| Состояние current build | Permanent calendar | Year overrides | Заметки |
|---|---|---|---|
| Чистый запуск, до фонового чтения | Bundled revision3 | Bundled4 manual | Bundled6 |
| Чистый запуск, успешное фоновое чтение текущего production | Bundled3: server3 не старше | Server15, независимо от permanent revision | Bundled6: серверная revision 4 меньше bundled 6 |
| Полный свежий local cache при том же CONTENT_REVISION/token | Сохранённый локальный выбранный набор | Сохранённый local набор | Уже загруженный результат |
| Новая server revision больше 3, действительно обнаружена | Replace всем permanent набором этой публикации | Отдельная загрузка year collection | Только notesRevision > bundled6 и успешный reader |
| Offline | Сохранённый полный cache либо bundle | Сохранённые либо bundled | Bundle/сохранённый chunk; актуальность сервера не гарантируется |

Имеет значение именно численное сравнение: Firestore заменяет permanent definitions только при revision>3 и совместимой schema на network path. При нынешней revision3 пользователь current build получает permanent bundle; его значения всё равно совпадают с production. Year collection загружается отдельно и способна менять day results даже без увеличения meta revision; в текущем snapshot 15 против 4 дают **0 поведенческих отличий**, поскольку extra auto совпадают с вычислением.

Это не доказывает, что каждый реальный установленный старый PWA уже имеет этот build или свежий cache. При complete cache и неизменном CONTENT_REVISION/token `refreshCalendarDefinitions()` может вообще не вызвать сетевой loader. После получения новых definitions `resolveRuntimeDay` способен вернуть старый memo для уже посещённой даты. Поэтому ответ на вопрос «увидят ли старые пользователи прежние празднования?» — **да, это возможно по воспроизведённым cache-путям**, а не измеренный процент пользователей.

## 9. Ошибки выбора празднования по умолчанию

Сам по себе wrong rank не меняет каждый год: воскресенья/старшие дни могут подавлять память. Поэтому используются полные ролевые счётчики, а не вывод по единственному 2026. Существующие before/after data-only516 дат первой фазы остаются условной моделью: она не решала C и не исправляла алгоритмы. Новая фаза добавляет проверенные нормативные cases.

## 11. Все спорные литургические вопросы

C01–C23: окончательная область/ранг 23 дополнительных назначений. C24: Braslau identity/Office/readings. C25–C28:4 точных manual-year исключения. C29: provisional High Priest +feast choice. C — не синоним «незаконно». Общее право, approved собственный календарь, local church calendar и годовая компетентная практика имеют разную область. ## 17. Риски и откат

Rank restoration меняет default, psalmody/Office kind и иногда доступные чтения; дата меняет назначение в двух днях; assignment removal может скрыть proper route; Braslau identity может перепривязать content; годовые записи имеют отдельный update/cache канал. Эти последствия отражены в каждой строке DECISION_MATRIX. Наличие текста не позволяет создавать отдельное календарное назначение, а removal назначения не даёт разрешения удалить текст.

Откат должен восстанавливать private calendar dataset под **новой большей revision**: например, плохой 4 заменяется восстановленным 5, а не понижением metaдо 3. Годовые документы восстанавливаются отдельно поmanifest, runtime-код — отдельным обратимым release; epoch/memo и payload caches проверяются после получения восстановленного набора. NotesRevision не понижать по одной разности count. При сохранении текстов и ID откат assignments не требует восстановления удалённых служб. Всё это план, write/deploy действий сейчас нет.
