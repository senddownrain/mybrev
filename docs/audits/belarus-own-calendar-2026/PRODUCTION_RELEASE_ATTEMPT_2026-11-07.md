## 7. Подготовленный механизм применения

Добавлены отдельные `scripts/ordo/publish-approved-calendar.mjs` и узкий REST adapter. Существующий planner остаётся read-only.

По умолчанию выполняется локальный dry-run. Live preflight читает только четыре разрешённых календарных ресурса. Apply требует явных `--live --apply --confirm-hash`, project `ibreviaryby`, точный неизменяемый seal исходного плана, schema/revision/notes, все ID/hash/updateTime, counts и before fields. Дополнительно используется exact hash, включающий технические поля; вложенное поле не может обойти seal через исключения canonical hash.

Применение спроектировано как одна read-write Firestore transaction с одним commit из 72 writes, строгими updateTime/exists preconditions и атомарной публикацией meta. Нет массового импорта, удаления, автоматического retry или автоматического восстановления данных. Маркер попытки записывается до commit; неопределённый результат требует отдельной read-only сверки. Readback проверяет все документы и 72 результата, включая неизменённые документы и серверное время meta.

Локальный dry-run исходного snapshot прошёл. Live preflight корректно отказал на новых notes. **Инструмент не прошёл реальное применение и не разрешает новый 71-operation plan**: его seal намеренно остался старым. Для продолжения требуются приёмка нового точного diff, обновление защиты под принятый план, проверка текущей базы перед записью и повторные финальные gates. Нельзя просто заменить digest при запуске или снизить notesRevision.

Dev dependency `https-proxy-agent` объявлена явно; версия 7.0.6 уже присутствовала в lockfile. TLS-проверка сохранена. Сетевой npm install был недоступен (403); новые версии пакетов не загружались.

## 12. Откат

Откат этой попытки не нужен: production не изменён. Приватный blueprint исходного 72-operation plan проверен offline: возврат прежних полей, восстановление 42 отключений, обратные 26 updates, отключение трёх новых ID без удаления текстов, metadata только под **новой revision 5**, publishedAt через REQUEST_TIME. Неизменяемые текстовые коллекции в него не входят. Монотонный epoch должен заставить клиентов перечитать календарь.

Этот старый blueprint с notesRevision 4 **не применим к текущему production**. Для нового предложения нужно подготовить принятый inverse с notesRevision 6, свежими post-release hashes/updateTime для всех затронутых документов и отдельным решением после сверки. Возврат на revision 3 и слепой автоматический rollback запрещены. Новые независимые изменения после публикации должны блокировать старый inverse.
