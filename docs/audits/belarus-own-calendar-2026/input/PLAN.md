# План нормативного аудита календарей Беларуси — MyBrev Web → Flutter

**Контрольная редакция:** 2026-11-03. **Сфера:** все четыре диоцезии, постоянные празднования + даты их фактического применения. **Начальная задача:** только исследование, отчёт и безопасные тестовые инструменты; публикацию и изменения действующих календарей не делать.

## Исходный принцип

- Главный предоставленный нормативный ориентир — приложенный `SOURCE_Ulasny_kalyandar_dyiacezii_na_Belarusi.pdf` (13 страниц). Он **претендует на полноту** собственных празднований, утверждённых согласно протоколам `2366/96/L`, `2270/96/L`, `796/03/L`, `417/12/L`, `371/00/L`, `209/23`. Претензию принимаем как рабочее допущение, не как независимую проверку текстов каждого римского декрета.
- PDF состоит из Общего римского календаря (в том числе для Европы), общебелорусских празднований, и особенностей 4 диоцезий. `*` отмечает собственные празднования. **Если литургическая степень не указана, согласно примечанию на странице 1, это необязательное воспоминание**. Нельзя считать отсутствие подписи «не праздник вообще».
- Уточнения/добавления к **Общему римскому календарю**, официально внесённые Римом позже редакции PDF, требуют самостоятельной проверки, с датой и первоисточником. Не подменять ими самостоятельное диоцезальное право.
- Ежегодные Ordo: Минск 2025–26, Витебск 2025–26, Пинск 2026, Гродно 2027 — это **доказательства фактической практики**, но не замена утверждённого постоянного собственного календаря.
- Частное храмовое/общинное/монастырское празднование не становится празднованием всей диоцезии. Обнаруженные тексты остаются в content storage, даже если убираем неправомерное календарное назначение.
- Декрет `04/P/20` о IV томе белорусской Литургии часов — **о переводе/использовании текстов**, не о включении святых в диоцезальный календарь. Сайт `https://lh.catholic.by/dekrety.php` — дополнительный источник переводческих декретов. Он не подтверждает св. Варвару.

## В какие проекты и где

- Этапы A–D: **Codex Cloud** в `senddownrain/mybrev`, новая ветка от актуального `main`; модель **GPT-6 Astra / High** (или xhigh для спорных правовых/литургических случаев).
- Этап E: `senddownrain/ibreviarybyapp` только после утверждения исправлений Web; **GPT-6.1 Sol / High** для механического переноса и паритетных тестов. Astra для спорных финальных решений.
- Локально: только когда нужен приватный Firestore, специальная конфигурация/ключи, воспроизведение на реальном Android/iOS или незапушенные ветки. Ни на одном этапе не менять `main` напрямую.

## А. Инвентаризация источников и кода (read-only)

1. Зафиксировать `git rev-parse HEAD`, дату, ветку, `git status`, все используемые источники, хеш PDF и версии данных.
2. Из PDF вручную и/или воспроизводимым парсером построить **эталон** `YYYY-independent` для 12 месяцев: `celebrationId`/название, MM-DD/движимое правило, место применения (general/europe/belarus/диоцезии), rank (solemnitas/festum/memoria/memoria-ad-libitum), номер страницы, дословный фрагмент. Неотмеченный ранг = необязательное воспоминание; исключения/перекрытия документировать. Включать все празднования, а не только строки со звёздочками, иначе не поймём точный результат каждого дня.
3. Сверить с официальным актуальным **Общим** календарём: дополнения Рима после публикации PDF хранить отдельно с ссылкой на акт. Не приравнивать отсутствие такого изменения в PDF к ошибке.
4. Определить реальные источники запуска: `src/data/ordo/calendar-definitions.json`, `src/constants/fixedCalendar.js`, `src/utils/ordo/definitions.js`, `src/utils/ordo/yearPlan.js`, `src/utils/ordo/display.js`, `src/utils/ordo/precedence.js`, `src/utils/ordo/*`, `src/data/ordo/layers.js`, публикация `liturgicalCelebrations` и `liturgicalDioceseOverrides` в Firestore, bundled snapshot, Flutter `assets/content/*.gz`.
5. Выяснить, какие файлы generated, а какие editable; **не исправлять только generated output** — он будет перезаписан.

## B. Полный differential audit (read-only)

1. Для каждой из 4 диоцезий выявить по каждому празднованию: `MATCH`, `EXTRA_NOT_IN_OWN_CALENDAR`, `MISSING`, `RANK`, `DATE`, `DIOCESE_SCOPE`, `TITLE`, `TRANSFER_OR_PRECEDENCE`, `MISSING_PROPER`, `UNIVERSAL_UPDATE`, `POSSIBLE_LOCAL_ONLY`, `NEEDS_DECREE`, `PARSER_UNCERTAIN`.
2. Отдельно проверить все 75 действующих диоцезальных записей из текущего snapshot (пересчитать по HEAD), весь общебелорусский слой, все универсальные даты/динамические правила и все текущие candidate rules; не ограничиваться первыми 10 нарушениями.
3. Все обнаруженные additions из ежегодных Ordo, но отсутствующие в PDF, маркировать для проверки; **без независимого документа** не считать доказанным правом диоцезии. Если в General Calendar действительно имеется тот же святой/день, не считать его автоматически местным дополнительным празднованием.
4. Для каждого расхождения предоставить: `id`, тип, епархия, дата, текущее представление/ранг, эталон/ранг, как это проявляется в UI (primary/alternative/commemoration/suppressed), источник PDF/страница, доказательство из исходного кода (путь:строка), уровень уверенности, предлагаемое действие; для неопределённых — конкретный вопрос комиссии.
5. Проверить особые случаи: два совпавших обязательных воспоминания; переносы в пост, Адвент и на воскресенье; 8 сентября в Витебске (две одноранговые формулировки); храмовые титулы и посвящения; 1/2 Vespers; default. Юридическую оценку не смешивать с текстовой полнотой служб.
6. Прогнать один и тот же анализ для годов 2025–2035 по 4 диоцезиям; **эквивалентность Web и Flutter не считается юридической правильностью** — оба приложения могут повторять одну ошибку.

## C. Сдать читаемый отчёт до массовых исправлений

Отчёт `docs/audits/belarus-own-calendar-2026/REPORT.md` + машинная таблица `diff.csv` + `source-manifest.json`/`evidence.tsv` (названия файлов примерные). Отдельно:
- сколько всего в эталоне, сколько диоцезальных additions/modifications;
- сколько совпадений и конфликтов по каждому типу/диоцезии;
- какие изменения безопасны и однозначны;
- какие требуют решения комиссии или отдельного декрета;
- какие runtime-правила и generated artifacts будут затронуты;
- dry-run перед/после по датам для Pinsk, Grodno, Minsk, Vitebsk;
- какие тесты выполнены, что заблокировано средой.
**Стоп-критерий:** прежде чем менять пользовательский календарь, отдельная приёмка отчёта человеком. Нельзя автоматически отключать все отсутствующие в PDF записи, пока не исключены актуальные изменения General Calendar и локальный контекст.

## D. Исправление нормативных данных (отдельная задача/PR)

1. Из утверждённого `diff.csv` разработать узкую миграцию календарных назначений; текстовые документы, `days`, `readings`, гимны, ноты и переводы не удалять.
2. Убрать неподтверждённые изменения ранга; восстановить реальные диоцезальные различия; не переносить праздник по одному ежегодному Ordo в постоянный календарь без основания.
3. Не менять без отдельного основания литургические алгоритмы, Advent 17–24, другие текущие feature-ветки.
4. Поправить seed/source-of-truth → generated JSON → Firestore публикационный план (с read-only dry-run!) → Web runtime. Не публиковать в продакшен автоматически.
5. Записать происхождение каждого override: `sourceDocument`, `page`, `authorityClass`, `status` (confirmed/unverified/general-update), trace to evidence. Для отсутствующих оснований — без утверждения окончательной законности.
6. Тесты: targeted node test, `npm run test:ordo`, `npm run ordo:check`, `npm test`, `npm run build`. Не запускать `npm run lint` на аудите, потому что проектный скрипт использует `eslint . --fix`; для read-only использовать `npx eslint .`.
7. PR с diff и таблицей каждой изменённой календарной записи; без авто-merge/автодеплоя.

## E. Flutter после Web

1. Подтянуть утверждённые определения/снимок и обновить content bundle. Раздельно сверить, нет ли актуального Hive overlay, которое перезаписывает bundle неверными данными.
2. Обновить parity fixture и запускать Dart тесты: `flutter analyze`, `flutter test`, targeted ordo/lectionary/hours parity; проверять bundle versus published source.
3. Проверить работу без сети и поверх старой установленной версии. Flutter PR отдельно, никаких изменений packageName, подписи, магазина и аналитики.

## Что считать успехом

- Каждый элемент из эталона покрыт, каждый дополнительный кандидат объяснён, у каждого расхождения есть доказательство/статус.
- Нет неподтверждённых диоцезальных календарных назначений **по умолчанию** и нет самовольного повышения ранга.
- Одинаковое нормативное поведение Web и Flutter после переноса, с учётом конкретной диоцезии и года.
- Исходные литургические тексты не утрачены; production не менялся без отдельного разрешения и проверки.
