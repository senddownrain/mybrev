## Что переносить

Первичные тексты исправлены в Web `patchs/feasts/common-texts/*.json`, собственных `patchs/feasts/*.json`, `patchs/json/ordinary-w5-d1-fixed-day.json` и `ranked-fixed-days.json`. Изменения только generated JSON переносить вручную нельзя: повторная генерация должна воспроизводить источник.

Основные данные: отдельная Ant-пара вместо избыточной копии в Ps; прописные заголовки кратких чтений/респонсориев; логические абзацы реплик; подтверждённые тире в просьбах; три полных аттестованных респонсория. Остальные сокращённые ответы оставлены для ручной сверки, включая варианты I Нешпар мученика/мученицы и неподтверждённые респонсории длинных чтений.

## Коллекции и поля

Синхронизировать согласованные изменения `liturgicalTemplates`, `liturgicalProperTexts`, старых materialized `days`. `invitatoriums` и `completoriums` проверены, но этим планом не изменяются. Bible, readings/Імша, prayers, songs, compendium в scope не входят.

Полный список 73 полей — `field-registry.json`: `officeOfReadingsHymn/Ant1–3/Ps1–3/Vers/R1/R2/Pr/TeDeum`, `laudes*`, `sext1*`, `sext2*`, `sext3*`, `vesper*`, `vesper1*`. Сохранять вложенные `_seasonalVariants` (`advent`, `christmas`, `lent`, `easter`), Marian `_mainSection`, `_fieldRules`, настоящие альтернативы и разреженное наследование. Отсутствующее поле не заполнять собственным текстом.

Календарные коллекции (`liturgicalCalendarMeta`, `liturgicalCelebrations`, `liturgicalDioceseOverrides`, `liturgicalYearOverrides`, `liturgicalOrdoNotes`) необходимы для parity и согласованного поколения ContentStore, но этот PR не предлагает новые календарные определения. По старому snapshot данные в bundle не обновлять.

## Какие Dart-алгоритмы адаптировать

Найти фактические текущие Dart-файлы по поведению; названия путей здесь не выдумываются, поскольку второй репозиторий не исследовался в этой работе.

1. **Psalm HTML/psalmody renderer.** До/после псалма рендерить отдельную Ant-пару. Удалять legacy-встроенный повтор только при совпадении целого заключительного абзаца с единственной отдельной антифоной. Метки `Ант.`, `1 ант.`, `2 ант.`, `3 ант.`, разбитые span, NBSP и регистр метки равноправны. При отсутствии отдельной антифоны, разных вариантах или несоответствии сохранять текст. Одна антифона на три псалма должна обрамлять группу. Варианты Ps3 Афіцыя за памерлых со своими антифонами не подменять общей Ant3.
2. **Reading/lection/responsory renderer.** Обрабатывать существующие абзацы и явные К./Н. как отдельные реплики; заголовок и ссылка — одна строка, тело чтения — отдельное. Поддержать корректное старое HTML. Малые часы остаются с двумя репликами. Не раскрывать сокращения на устройстве универсальной формулой. Три проверенных полных текста приходят из данных; правила расширения нужны только Web-генерации/аудиту.
3. **Intercessions.** Убрать чередование petition/response по индексу и окраску первой буквы. Приоритет: явно проверенный `data-intercession-role` (если встречается), начальное тире, точный повтор рефрена, структурно незавершённое обращение и продолжение со строчной буквы. Неоднозначные строки не признавать ответами. Красный — только знак тире, а не буква обычного абзаца. Повторяющиеся аккламации не получают тире.
4. **Evening resolution/list/router.** Право на I Нешпары даёт Ordo descriptor, а не наличие `vesper1*` и не один `rank == festum`. Для неизвестного legacy descriptor использовать консервативный fallback урачыстасці. Одна карточка на празднование/епархиальный scope, Common — выбор текста внутри него. Сохранить оба старых Common dayId как alias; прямая ссылка не должна обходить права текущей епархии. Не подставлять первую primary-карточку, если celebrationId не найден.
5. **Common materialization/assembly.** Проверить прежний порядок сезон → Common → собственные поля, `_mainSection`, правила, ref/omit и епархиальные ранги. Нового обязательного поля/изменения schema этот PR не вводит.
6. **ContentStore.** Проверить принятие нового baseline поверх старого overlay и атомарное поколение связанных литургических коллекций. SHA документа — прежний алгоритм из `docs/app-content-distribution.md`; не менять хеширование одной платформы. Старые локальные данные должны уступать более новому bundle, синхронизация не должна повторно дописывать HTML.

## Данные и публикация: текущие ограничения

Свежий Web snapshot (13.11 21:53 UTC) подтверждает наличие полных славословий в Firestore: 1 082 документа, 16 049 полей/правил, 0 дополнений. Но опубликованный manifest от 08.11 отстаёт: 276 days и 11 templates; Proper collection в manifest отсутствует. Состояние Flutter bundle/выпущенного приложения ещё не проверено.

Dry-run этого PR: 975 документов / 9 041 поле / ~60.65 MB хранимых изменённых документов. Вердикт **MASS CONTENT REBUILD**. Это не SAFE CONTENT PATCH. Применять dry-run без нового snapshot, проверки beforeSha256/updateTime и отдельного разрешения нельзя.

Нельзя публиковать:

- неподтверждённые полные ответы из manual-review;
- массовый манифест через `--allow-large-patch`;
- bundle из устаревшего snapshot или не прошедший `content:app-release --compare-live`;
- новую коллекцию в manifest до релиза приложения с этой коллекцией;
- Web content revision до согласованной публикации данных;
- изменения Firestore, Hosting deploy и Flutter release без отдельного разрешения.

После разрешённой записи: readback точных полей → повторные аудиты → свежий snapshot → проверенный новый bundle → отдельный Flutter PR/CI/визуальная приёмка → согласованный релиз → манифест по штатному порядку. Версию schema не повышать без реального изменения контракта и согласованного релиза обеих платформ.
