# Firestore Spark: аудит квоты и Connection failed — 14.10.2026

Исходная версия: `origin/main` = `18ac50a`. Изменения подготовлены в отдельном
worktree. Production Firestore, Rules, Authentication, коды и данные не менялись;
Hosting не публиковался. Анализ использовал исходники и существующие локальные
снимки. Обновление снимков и массовые запросы не запускались. После локальных

## Вывод и граница доказательства

Наиболее вероятная причина `Quota exceeded` — накопленная суточная нагрузка
Firestore (в первую очередь чтения), усиленная предзагрузкой, полными обходами
коллекций и повторами. Одна обычная смена кода делает **одну запись**, поэтому
сама по себе не объясняет исчерпание 20 000 записей. Пока нет метрик Console и
исходного SDK `error.code`, нельзя утверждать, что исчерпаны именно чтения:
возможны другая квота API, writes, Auth или иной предел.

Подтверждён отдельный дефект: успешный commit смены кода сопровождался
`getDocFromServer(settings)`. Ошибка этого последующего чтения превращала
подтверждённую смену в ошибку формы и теряла единственный показ plaintext-кода.
`Connection failed` на том же этапе имел бы такое же последствие.

Владелец сообщил, что операция успешно выполнилась после отключения VPN:
для наблюдавшегося `Connection failed` это указывает на сетевой путь VPN.
Не следует приравнивать эту сетевую ошибку к исчерпанию дневной квоты.

Проверка доступности без исполнения production-приложения: Hosting вернул HTTP
200; корневые URL Firestore и Identity Toolkit вернули HTTP 404, то есть DNS,
TLS и HTTP работали с проверявшей машины. Эти ответы **не проверяют** проектную
квоту, Anonymous Auth, Rules или успешность операций Firestore. На просмотренных
14 октября публичных Firebase/Google Cloud dashboards не было объявленного
широкого сбоя Firestore; это не исключает локальную или проектную проблему.
См. [Firebase Status](https://status.firebase.google.com/) и
[Cloud Service Health](https://status.cloud.google.com/).

Единственный live Firestore GET публичного `liturgicalCalendarMeta/current`
(маска одного поля) в 13:03 UTC / 16:03 Москвы 14.10 получил HTTP 200.
Это подтверждает доступность данной публичной операции в момент проверки;
не доказывает остаток writes, исправность VPN или всю административную цепочку.
Содержимое документа в отчёт/лог не сохранено. Сам offline audit делает 0
production reads; эта отдельная проверка соединения — один запрос, без повторов.

## Где именно возникает ошибка

`PriestAccess.vue:replaceCode()` вызывает `priestAccessService:replacePriestCode()`:

1. Проверка/генерация кода, вычисление proof в памяти.
2. Транзакция читает `priestAccess/settings`, меняет proof/дату, сохраняет help.
3. После подтверждения сервером выполняется необязательное чтение для проверки
   актуального proof и получения server timestamp.
4. Код возвращается форме только после этих действий.

Теперь ошибка шага 2 имеет безопасные поля `operation: code-transaction` и
`code`; подтверждение не выдумывается. Ошибка шага 3 возвращает подтверждённый
код с предупреждением и `warningCode`, не запускает вторую ротацию, оставляет
копирование доступным. Точная дата отмечается ожидающей подтверждения, пока
серверное чтение недоступно. Если другая сессия уже заменила proof и чтение это
подтвердило, устаревший код не объявляется действующим.

Административные чтения settings, реестра и проверки кода теперь используют
Firestore Lite с тем же App/Auth/Rules. В установленном полном SDK 10.14.1
одноразовый read использует Listen stream, который может внутренне уходить в
backoff при `resource-exhausted`; Lite делает один REST read. Транзакциям явно
задан `maxAttempts: 1`, поверх него разрешены максимум три попытки только при
`aborted`, `failed-precondition` или `already-exists` — сигналах конфликта
оптимистической транзакции. `resource-exhausted` не повторяется.

Если commit потерял сетевое **подтверждение**, его исход неоднозначен. Это другой
случай: сервис не заявляет успех и не повторяет такую смену автоматически.
Гарантия сохранения кода относится к commit, уже подтверждённому сервером.
Код остаётся только в памяти текущей формы; закрытие страницы уничтожает его.

## Различение ошибок

| Код/сигнал | Обработка |
| --- | --- |
| `resource-exhausted`, gRPC 8, `auth/quota-exceeded` | Белорусское сообщение о квоте; немедленная остановка повторов |
| `permission-denied`, gRPC 7 | Отдельное сообщение о правах; активация сохраняет сообщение о неверном/заменённом коде |
| `unavailable`, gRPC 14, `deadline-exceeded`, gRPC 4 | Сообщение о временной недоступности/соединении |
| `auth/network-request-failed`, известные transport errors, `Connection failed`, `Failed to fetch` | Сообщение о соединении; не объявляются квотой |
| `unauthenticated` | Необходимость повторного входа администратора |
| Остальные | Безопасная общая ошибка либо существующая локальная ошибка валидации |

Код SDK имеет приоритет над текстом. Одна строка `Quota exceeded.` без code не
доказывает Firestore-квоту: браузерный `QuotaExceededError` относится к локальному
хранилищу. В логах общий обработчик Firestore оставляет код, без тела запроса,
proof, токена или исходного сообщения backend.

| `PriestAccess.vue` | Был автоматический обход всех страниц устройств по 100. Теперь только 25 документов, следующие страницы — явной кнопкой; повторный load во время работы блокируется |

| `prayerContentService.js` | Общий in-flight запрос, две публичные коллекции, две защищённые только после проверки grant. Убрана дополнительная проверка grant при quota-отказе защищённого чтения. Публичная серверная перепроверка сохранена |
| `prayerStorageService.js`, prayer stores | Четыре общие подписки, а не отдельные четыре для каждого store. Сохранение читает все четыре коллекции и дважды control/version, затем transaction control. Это нужно для безопасного переноса наследуемых ограничений; алгоритм и Rules не заменены |
| Календарь | Месячная сетка использует локальный Ordo engine, без запроса на каждую ячейку. Startup проверяет meta и year overrides; новый remote revision дополнительно читает celebrations/diocese overrides; notes загружаются по необходимости |
| Hours / Readings | Чтения по canonical ID, дате, периоду и feast; пустые fallback queries тоже стоят чтение. Существующие revision cache и in-flight dedup сохранены |
| DayEditor / ParsedReadingEditor | Online-first документ, proper/связанные readings и дополнительные тексты по необходимости. Не массовый автоматический importer, но открытие/сохранение добавляет reads/writes |
| Songs / Compendium / Bible | Songs и Compendium — полная публичная коллекция при cold load, затем revision cache. Bible — документ выбранной книги. Учитывать и объём трафика, не только количество reads |
| Bible upload | Старый retry повторял любой отказ до шести раз. Теперь quota и permission остановлены сразу; сам importer не запускался |
| `resync-readings.mjs` | Добавлен безусловный запрет quota retry до проверки transient-текста; остальные существующие ограничения сохранены |
| Импорты / аудиты / backups | Полные live scans повторяются при plan/backup/verify; read-only/dry-run не означает бесплатный. Предпочитать local snapshot analysis, затем отдельный разрешённый apply |
| Flutter manifest / sync | `publish-manifest.mjs` без `--snapshot` читает все выбранные коллекции даже без `--apply`, затем manifest/digests. App bundle исходно локальный; `--compare-live` добавляет live reads. Не запущены и не изменены |

Новый `db:audit-firestore-usage` обязательно требует локальный `--snapshot`.
Он не импортирует Firebase SDK и не имеет режима записи. Отчёт содержит только
даты/числа документов и кандидаты вызовов в исходниках; не IDs, подписи или proof.
Inventory — статический список кандидатов, не измерение реального исполнения:
aliases, wrappers, динамические обращения и Admin SDK требуют ручной проверки.

В памяти добавлен circuit breaker: обнаруженная квота блокирует новые обращения
через охваченные helpers, prefetch и автоматические проверки grant. Явная кнопка
повтора/обновления или перезагрузка позволяет проверить восстановление. Уже
запущенные параллельные запросы и внутренний transport backoff существующих
полных SDK listeners могут завершаться отдельно; приложение не обещает
глобальную отмену всех SDK RPC. Listener отзыва и Rules не ослаблены ради квоты.

## Оценка операций

[Бесплатные пределы Firebase](https://firebase.google.com/docs/firestore/quotas):
50 000 reads и 20 000 writes в сутки, сброс примерно в полночь Pacific. Для
14 октября (PDT) это около 10:00 Москвы. Это не срок действия priest grant.

Исторические локальные снимки: 27.08 — 743 legacy `fixedDays` (не текущие `days`);
12.10 13:22 UTC — 85 публичных молитв, 4 публичные категории, 21 защищённая
молитва, 1 защищённая категория; 12.10 18:22 UTC — 4 grants. Они не покрывают
всю базу и не показывают сегодняшнюю нагрузку.

Обозначения: P/C — публичные молитвы/категории, Q/K — защищённые, G — grants,
H — чтения новой даты Hours, R — новой даты Readings, S — общие статические
документы. Каждую пустую query считать минимум как одно чтение.

| Сценарий | Ориентир reads | Writes |
| --- | --- | --- |
| Cold opening молитвенника, раньше | P+C+S+9×(H+R)+startup | 0 |
| Тот же сценарий после исправления | P+C+S+2×H+startup | 0 |
| Cold opening только Hours | S+2×H+startup, без P+C если молитвенник не открыт | 0 |
| Повтор публичного молитвенника online | P+C на перепроверку | 0 |
| Перелистывание месяца календаря | 0 дополнительных content reads; startup/новая публикация отдельно | 0 |
| Новая дата Readings | R; повтор готовой даты по той же revision обычно 0 | 0 |
| Prayer admin initial listeners | P+C+Q+K, затем изменённые docs/reconnect | 0 |
| Сохранение молитвы/категории | P+C+Q+K+3 version/control reads; conflicts добавляют попытки | Изменённые/перенесённые docs + control |
| DayEditor | 1 day + proper doc + дополнительные invitatorium/Compline; связанный ReadingEditor может читать linked readings | Только изменённые документы |
| Priest admin, раньше | 1+G, плюс empty final page если нужна | 0 |
| Priest admin, теперь | 1+min(G,25); каждая дополнительная страница до 25 | 0 |
| Смена кода | 1 transaction read + 1 optional read | 1, **0 grant writes** |
| Сохранение инструкции | 1 transaction read | 2, без повторного metadata read |
| Новая активация | 2 explicit grant reads + listener и Rules | 2 (claim+grant) |
| Статус уже активного устройства | 1 grant read на вызов + listener; protected fetch Q+K | До 1 activity write/час на установку |
| Подпись/отзыв устройства | Rules reads | 1 |
| Live импорт k изменений | Scan N + verification N или k + отдельные manifests/backups | k |
| Live manifest dry-run | ΣN выбранных коллекций + current + changed digest docs | 0 |
| Manifest apply | Новый такой scan + digests/verification | changed collections + current |

**Иллюстрация**, а не измерение: H=10, R=8, S=30, P+C=89, startup=2 дают
283 → 141 reads при cold opening молитвенника (~50% меньше). При G=1000
первое открытие реестра: 1001 → 26 (~97% меньше). Если бы только такие cold
opening расходовали квоту, 50 000/283 ≈176 против 50 000/141 ≈354 открытий.
Реальная ёмкость ниже: параллельно работает весь проект, включая Flutter и CLI.

По [правилам подсчёта Firestore](https://firebase.google.com/docs/firestore/pricing)
отдельно добавить зависимые Rules reads (`admins`, grant, settings/control),
минимум одного read на пустую query, изменения/reconnect listeners и применимые
index-entry charges. Memory-only listeners при переподключении перечитывают
набор. Не считать повторный get одного зависимого Rules документа как отдельный
read на каждый вызов функции в одном запросе. Это ориентиры, не счёт Firebase.

## Какие измерения подтвердят причину

1. Firebase Console → Firestore → Usage: reads/writes/deletes за сутки и график
   вокруг времени ошибки; объём данных и network egress. Указать время/часовой пояс.
2. Google Cloud → API/Quotas для Cloud Firestore API: **точный metric/limit**, а
   не только текст Quota exceeded; уровень daily quota или иной лимит.
3. Сравнить всплески с посещениями, admin tabs, CLI импортами, snapshot exports,
   manifest runs и Flutter sync. Не запускать новые live scans ради сравнения.
4. При следующем отказе записать только SDK code, action/operation и время.
   Разделить transaction/Commit и последующий BatchGet; для Connection failed
   проверить браузерный network status, DNS/VPN/proxy и `auth/network-request-failed`.
   Не сохранять request payload, proof, токены или полный HAR.

Отдельная ошибка read после успешного Commit подтверждает риск потери кода;
отказ до/на Commit не подтверждает его сохранение. Для вывода об исчерпании
дневных reads нужен соответствующий Console график/лимит.

## Проверки и дальнейшая эксплуатация

Добавлены тесты quota/permission/network, единственной попытки при quota,
отсутствия перекрывающихся timeout-reads, подтверждённого кода после ошибки
проверки, конфликтующих транзакций, bounded prefetch, пропуска админки,
сохранения public offline cache и offline audit без приватных данных.
Эмуляторный UI дополнительно проверяет реальную смену, подтверждение/отказ,
сохранение единственного кода при Refresh, ручную пагинацию, атомарные claims,
отзыв и перезапуск. Только local demo project; внешние UI запросы блокируются.
Числа финального прогона и SHA приведены в PR.

При quota не нажимать смену многократно. Если показано «Код захаваны серверам» —
скопировать код, не создавать другой из-за предупреждения; текущие устройства
не затрагиваются. Если запись не подтверждена — сначала восстановить соединение
и проверить состояние; не обещается восстановление plaintext из хеша.

Для предотвращения повторения: следить за Usage, закрывать ненужные editor tabs,
использовать существующие local snapshots для планов, считать ΣN перед
разрешённым live export/import, ограничивать коллекции manifest publication.
Не обновлять snapshot автоматически и не проводить массовые работы при
неизвестной остаточной квоте. Большие перестройки отправлять новым app bundle
по существующей инструкции, без bypass её guards. Rules/авторизация/Blaze
в этом исправлении не менялись.

Публичные сохранённые данные остаются offline; автоматом заранее готовятся
Hours сегодня/завтра вместо девяти дат. Readings для offline нужно открыть
online заранее. Закрытые тексты остаются только в памяти и требуют действующего
серверного grant; offline-копия grant не даёт доступ. Поиск реестра применяется
к загруженным страницам, это явно указано в UI; все страницы доступны вручную.
