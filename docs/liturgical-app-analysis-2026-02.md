# Анализ приложения (Vue + Vuetify + Firebase + PWA)

## Контекст
Приложение решает три связанные задачи:
- отображение **Литургии часов** (коллекция `days`);
- отображение **литургических чтений дня** (коллекция `readings`);
- хранение **молитв-пометок по тегам** (коллекция `prayers`).

Основа вычислений — календарные данные `yearOptions` + динамические даты (Пасха и связанные праздники).

---

## 1) Что уже реализовано хорошо

1. **Единая вычислительная база для дат.**
   Есть `computeLiturgicalContextForDate`, который вычисляет контекст дня без прямого чтения `days`.
2. **Кэш-прогрев уже встроен.**
   `warmupCache()` грузит `yearOptions`, `prayers`, `readings`, `days` и делает предзагрузку на месяц вперед.
3. **PWA-режим включен.**
   Сборка формирует service worker и precache.
4. **Разделение по доменам.**
   Логика чтений/дней/молитв разведена по composable/service/store слоям.

---

## 2) Где вероятна десинхронизация «Литургия часов vs Чтения»

### 2.1. Разные ключи/написания праздников
В `feastNameMap` есть как минимум один критичный маппинг, который выглядит ошибочным:
- `corpusChristi` сопоставлен с `palmsunday` (явная потенциальная причина несоответствия).

Также заметны рискованные места по орфографии ключей:
- `baptismOfLord` -> `buptismofthelord`;
- `palmsSnday` (в самом ключе пропущена `u`).

Даже если часть этих строк исторически «совместима с БД», они создают высокий риск расхождений между подбором `days` и `readings`.

### 2.2. Поиск чтений агрегирует несколько стратегий
`getReadingsForDate` делает несколько запросов (по `_date`, по периоду, по `_feast`, с/без `cycle`) и потом объединяет. Это полезно для полноты, но может отдавать «не тот» документ первым без строгой приоритизации по литургическому рангу.

### 2.3. Типы и формат полей
В разных местах присутствует риск несогласованности типов (`number` vs `string`) для `_periodWeekNumber` / `_dayOfWeek` и различий по дате (`D.M` vs иные форматы в legacy-данных).

## 3) Кэширование на 30 дней: текущее состояние и улучшения

### Уже есть
- В `warmupCache()` выполняется прогрев на **30 дней вперед** для `readings` и `days`.
- Есть механизм `ensureDaysCacheCoverage()`, который догружает окно, если покрытие ослабевает.

### Чего не хватает для «гарантированных 30 дней»
1. **TTL/версионирование собственного кэша.**
   Сейчас полагаемся в основном на persistent cache Firestore. Для предсказуемости лучше добавить «метаданные прогрева» (дата последнего полного прогрева + диапазон).
2. **Периодический re-warmup.**
   Запускать фоновую проверку 1 раз в сутки (или при старте), чтобы поддерживать непрерывное окно `today..today+30`.
3. **Наблюдаемость.**
   Логировать % покрытых дней, среднее время ответа из кэша/сети.

---

## 4) Молитвы как заметки с тегами

Текущая модель «молитва + категории/теги» хороша для MVP. Для развития:
1. Добавить **иерархию/алиасы тегов** (например, «утро» включает подкатегории).
2. Добавить **избранное + умные подборки** (по времени суток/литургическому сезону).
3. Добавить **офлайн-first UX** (пометка «сохранено локально / синхронизировано»).

---

## 5) Дизайн/UX: что доработать в первую очередь

1. **Единый экран дня**: в одном месте показывать
   - период/неделю,
   - Литургию часов,
   - чтения,
   - заметки/молитвы по тегам.
2. **Явная индикация источника данных**:
   - «из кэша» / «обновлено из сети»;
   - дата последней синхронизации.
3. **Диагностика расхождений (в админке)**:
   - «для даты X найден `days._feast=A`, а `readings._feast=B`»;
   - быстрый переход к исправлению записей.

## 6) Приоритетный план работ (предложение)

### Этап 1 (быстрые wins, 1–2 дня)
- Проверить и унифицировать `feastNameMap` (включая `corpusChristi`).
- Добавить диагностический отчёт «дата -> контекст -> найденные documents IDs» для спорных дат.
- Зафиксировать правила приоритета для результатов чтений (дата > праздник > период, либо по согласованному литургическому рангу).

### Этап 2 (устойчивость, 2–4 дня)
- Ввести метаданные локального кэша прогрева (TTL, диапазон, версия).
- Сделать ежедневный «лёгкий» re-warmup окна +30 дней.
- Добавить метрики cache hit/miss.

### Этап 3 (UX, 3–5 дней)
- Единый «экран дня» + статус офлайна/кэша.
- Улучшение фильтрации молитв по тегам и сохранённым подборкам.

---

## 7) Риски и как снижать

- **Риск:** исправление ключей праздников может «сломать» старые документы в Firestore.
  - **Снижение:** поддержать переходный слой alias-ключей на период миграции.
- **Риск:** агрессивный прогрев может увеличить сетевую нагрузку на слабых устройствах.
  - **Снижение:** батчи + приоритет ближних дней + ограничение по сети/батарее.

---

## 8) Краткий вывод

Проект уже имеет сильную базу (единый календарный контекст, PWA, кэш-прогрев).
Основная техническая причина текущей десинхронизации, с высокой вероятностью — рассогласование ключей праздников и нестрогая приоритизация результатов чтений.

Оптимальная стратегия:
1) сначала унифицировать feast-ключи и правила выбора чтений;
2) затем формализовать 30-дневный кэш (TTL + re-warmup);
3) после этого улучшать UX единого «экрана дня» и работу с молитвенными тегами.
