# Общие категории молитв: Web → Flutter, контракт v1

Утверждённый UX от 14.11.2026: иерархические страницы списков. Он заменяет
прежнее требование аккордеона в PR #246. Иконки интегрированы из merged PR #247.

Согласованный источник: Firestore ID категории, существующие `parentId`, `order`,
`tags`, `priestOnly` и **одно новое опциональное поле `prayerIds: string[]`**.
Эквивалентного общего механизма ручного состава в Web до этого изменения нет.
Личные категории (`personalPrayerCategories`) и скрытые стандартные категории
остаются пользовательскими настройками. Вложенность личных категорий не вводится.

```json
{
  "id": "mary",
  "name": "Марыйныя малітвы",
  "parentId": null,
  "order": 10,
  "tags": ["Марыя"],
  "prayerIds": ["existing-published-prayer-id"],
  "priestOnly": false,
  "iconKey": "virgin-mary",
  "iconId": "existing-legacy-icon-id"
}
```

`id` в JSON — ID Firestore-документа; запись не переименовывает/не пересоздаёт
документ. `icon`, `iconId` и неизвестные существующие атрибуты сохраняются при
редактировании. Основной атрибут иконки — `iconKey` из общего каталога 48
семантических ключей (36 Phosphor + 12 собственных SVG). `CategoryIconPicker`
сохраняется в общей админке и личных категориях; `CategoryIcon` рендерит ключ
через allowlist и доверенные bundled SVG, с fallback для неизвестного ключа.
Старые `icon/iconId` не удаляются. Неизвестный существующий `iconKey` сохраняется
при round-trip, пока администратор явно не выберет другое значение.
См. [контракт иконок PR #247](prayer-category-icons/README.md). `effectivePriestOnly` вычисляет хранилище;
редактор меняет только собственный `priestOnly`.

## Прямой состав и старые данные

Отсутствующий `prayerIds` означает `[]`; `tags` также может быть `[]`.
Пустая категория допустима независимо от наличия детей. Ручные ID уникальны,
непусты и указывают на опубликованные документы `prayers` / `priestProtectedPrayers`.
`prayerDrafts` не читается и не считается опубликованным каталогом.
Сохранение проверяет ID заново на актуальном каноническом наборе внутри атомарного
мутатора. Неизвестную ранее сохранённую ссылку редактор показывает отдельно и
требует явно снять; молчаливого удаления ссылок при открытии/сохранении нет.

Для категории C и молитвы P:

```text
tagged = intersection(C.tags ?? [], P.tags ?? []).isNotEmpty
manual = (C.prayerIds ?? []).contains(P.id)
legacy = C.id != null &&
         (P.categoryId == C.id || (P.categoryIds ?? []).contains(C.id))
direct = tagged || manual || legacy
```

Результат уникален по P.id. Потомки **не** расширяют теги или прямой состав родителя.
Причины в редакторе: «Па тэгах», «Дададзена асобна», «Абодва»; legacy-причина
дополнительно отмечается «Старая сувязь». Снятие ручного ID не снимает теговое или
legacy-включение. Выбор не переписывает теги, текст или флаг молитвы.

Удаление последнего тега всюду сохраняет категории, их детей и `prayerIds`.
Удалить родителя с детьми нельзя: сначала перенести/удалить детей. Удаление листа
сохраняет молитвы и снимает только его legacy `categoryId/categoryIds`; личные
настройки не переписываются. Удаление опубликованной молитвы через существующий
сервис очищает её ID в общих категориях в той же атомарной операции.

## Дерево, сортировка, маршруты

Соседи: числовой конечный `order` по возрастанию → `name.localeCompare('be',
{sensitivity: 'base'})` → ID для одинаковых имён. При отсутствующем `order` узел
идёт после узлов с порядком. Сохранять значения порядка при round-trip; старому
документу без порядка редактор предлагает 0. Одинаковые имена в разных ветках
допустимы, в одной ветке сохранение дубликата запрещено.

Самоссылки, циклы, неизвестный родитель и цепочка длиннее 64 узлов запрещены при
сохранении затрагиваемой ветки, включая её потомков. Прочие повреждённые ветки
не препятствуют их поочерёдному исправлению. Старые неверные связи закрываются
политикой доступа. Администратор видит повреждённые узлы как корневые для ремонта.
В публичном дереве такие узлы и заголовки отсутствуют.

Сначала применяется политика доступа, затем пользовательское скрытие, затем
строится дерево. Если разрешённый родитель скрыт **пользовательской настройкой**,
разрешённые дети становятся корнями; скрытие папки не скрывает автоматически
отдельные настройки её детей. Реально пустые ветки скрываются у читателя;
пустые родители непустых потомков сохраняются. Личные категории остаются плоскими
после общих; старое подавление личного дубля по имени общего раздела сохраняется.

Фактический Web entry point — `NavigationDrawer.vue`. Боковая панель показывает
**только корни видимого дерева и плоские личные категории** с собственным
`iconKey`. Нажатие открывает страницу категории; раскрытия, стрелок раскрытия,
`aria-expanded` и сохранённого состояния раскрытия категорий больше нет.

Порядок страницы выбранной категории:

1. Название категории и ссылка к видимому непосредственному родителю либо
   «Усе малітвы» для корня. Скрытый пользовательской настройкой родитель не
   возвращается через эту ссылку: его дети уже стали корнями.
2. Все видимые непосредственные подкатегории отдельными ссылками, каждая со
   своим `iconKey` и стрелкой **перехода**. Ни одна не раскрывается на месте.
3. Прямые молитвы текущей категории обычным существующим списком.

Лист сразу показывает обычный список молитв. Если прямых молитв нет, но дети
есть, видны только дети: ложного «Малітвы не знойдзены» нет. Отдельной строки
«Малітвы гэтай катэгорыі» нет: собственный список уже находится ниже детей.
На всех корректных уровнях до лимита используется одна и та же страница.
Админское дерево также всегда показано полностью с отступами, поиском и
родительским контекстом, без раскрывающихся узлов. Picker иконок может иметь
своё открытие панели выбора; это не аккордеон категорий.

Существующий маршрут получает опциональный query:
`/prayers?category=<Firestore-id>` (также работает на `/prayers/list`). Reader:
существующий `/prayer/:id`. Обычные ссылки сохраняют прямое открытие/новую вкладку
и browser Back/Forward. Каждый переход между категориями создаёт запись истории.
При новом переходе страница начинается сверху; browser history восстанавливает
scroll, а список возвращает фокус на открытую дочернюю категорию или молитву.
Вход по прямой ссылке фокусирует заголовок и корректно устанавливает название
страницы. Фокус молитвы не перехватывается при дальнейшем вводе в поиск.

Старые адреса без query остаются рабочими; недоступный или неизвестный ID даёт
пустой список без заголовков/содержимого закрытой категории. Пользовательское
скрытие — настройка меню, не запрет доступа: прямой URL скрытой, но разрешённой
категории остаётся рабочим. Теги из дополнительного фильтра применяются к
текущему прямому составу и сохраняются после reader/back. Личные категории
по-прежнему хранят выбор в сессии, без нового deep link.

Пример fixture: `Марыйныя малітвы` (собственные tagged/manual молитвы) →
`Ружанец` (своя молитва и дочерняя категория) → reader. Дополнительный уровень:
`Таямніцы ружанца`. Прямые списки каждого уровня независимы.

## Матрица доступа и физическое хранение

**Ограничение побеждает:** молитва закрыта, если собственный `priestOnly=true`
ИЛИ она связана хотя бы с одной эффективно закрытой категорией через теги,
`prayerIds`, `categoryId` или `categoryIds`. Наличие той же молитвы в публичной
категории не открывает её. Собственные флаги потомков не меняются при переносе.
Снятие последней закрывающей связи открывает молитву только при отсутствии
других причин ограничения. Битые parents, циклы и чрезмерная глубина fail-closed.

| Объект/операция | Public / без grant | Priest с активным grant | Admin |
| --- | --- | --- | --- |
| `prayers`, `prayerCategories` | Чтение | Чтение | Чтение |
| `priestProtectedPrayers`, `priestProtectedCategories` | Запрещено | Чтение | Чтение |
| Заголовки/тексты закрытых молитв в общем списке, поиске, публичном bundle | Отсутствуют | Только из защищённого источника | Из канонического admin-содержимого |
| Изменение общей структуры / членства | Запрещено | Запрещено | Атомарный мутатор + контроль версии |
| Личные категории / скрытие | Только собственные настройки | Только собственные настройки | Только собственные настройки |

Публичная категория может хранить **непрозрачный ID** молитвы, закрытой другой
связью. Это сохраняет ручную привязку для владельца grant и после открытия доступа.
По ID нельзя получить защищённый документ без разрешения; названия и тексты
не встраиваются в категорию. Клиент никогда не подставляет закрытые документы
в публичный список или постоянный cache. Не удалять такой ID при фильтрации
канонической модели: это потеряло бы настройку администратора.

Все изменения идут через существующий `mutatePrayerContent` →
`prayerStoragePlan`. Пересчитывается **весь** канонический набор, затем set/delete
обоих namespaces и увеличение `priestContentControl/state.version` выполняются
в одной транзакции. Лимит: 400 операций со змесцівам + control write, а также
существующий предел сериализованного плана 7 MB. План в редакторе — оценка по
подписке; непосредственно перед commit мутатор перечитывает состояние,
повторно валидирует и проверяет реальные лимиты/версию/lock. Превышение блокирует
сохранение с предложением проверенной миграции, частичных batch нет.

Firestore Rules не меняются: они уже требуют admin, согласованный control write,
отсутствие публичных `priestOnly/effectivePriestOnly` и запрещают защищённые чтения
без grant. Семантический пересчёт членства выполняет доверенный admin-мутатор,
как прежде для тегов и parent; Rules не обходятся и публичных write API не добавлено.

## Bundle, cache и поэтапный выпуск

Публичный gzip bundle и manifest используют существующий `publicAppCollections`
с **той же** `prayerAccessPolicy`; новые ID сериализуются обычным массивом.
`CONTENT_SCHEMA_VERSION` и формат gzip/string-table не меняются: поле опционально,
старые документы не переписываются для добавления пустого массива.
`prayer-category-contract.test.mjs` реально вызывает `writeBundle`, читает gzip
и декодирует коллекции: поле сохраняется, закрытые объекты/заголовки отсутствуют.

**Отдельного статического защищённого bundle в этом репозитории нет.** Защищённый
канал Flutter/Web — Firestore `priestProtectedPrayers` /
`priestProtectedCategories` под grant, с памятью вместо публичного disk cache.
`prayerIds` сохраняется в этих документах атомарным планом; тест проверяет также
round-trip существующего codec для защищённых категорий. Не создавать/не
публиковать защищённый архив через публичный Hosting.

Добавление поля меняет digest/структуру документов. Согласно
[app-content-distribution.md](app-content-distribution.md) и AGENTS.md это
согласовывается как новый bundle при выпуске приложения, а не принудительный
SAFE CONTENT PATCH. Никакой manifest/app-release/apply/deploy в этой задаче
не запускается. Нет live-аудита, production reads/writes, refresh snapshot или
изменения Flutter.

Совместимость: старый Flutter должен игнорировать неизвестное опциональное поле и
продолжать читать прежние public коллекции. До Flutter PR он не получит новую
семантику ручных членов и вложенности. Реальный старый Dart decoder/приложение
**требует проверки во Flutter-репозитории**: Web codec-тест не доказывает работу
старого бинарного клиента. Изменять тексты/искусственно добавлять теги ради него
нельзя. Выпуск: Web PR и контракт → Flutter PR → тест старого/нового приложения
на fixture и защищённом канале → отдельное решение владельца о публикации.
