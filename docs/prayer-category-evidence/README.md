# Подкатегории: реализация и приёмка

База: `origin/main` **5f36981** (14 ноября 2026). До реализации проверен список
открытых PR: #241–#243 — черновики/импорт, #245 — литургические тексты;
дублирующей реализации категорий не было. Эти ветки не объединялись.

Уже существовали: `parentId/order/priestOnly/tags`, админский редактор,
наследование доступа, public/protected collections, общий версионированный
атомарный мутатор. Меню было плоским и объединяло теги потомков, ручного общего
членства не было, снятие последнего тега удаляло категорию.

Реализовано: независимый `prayerIds`, единый OR matcher, прямой состав без
потомков, дерево/поиск с контекстом в текущей админке, создание подкатегории,
порядок и сохранение метаданных, picker 30 элементов/страницу с debounce 250 ms,
выбранные/cancel/done, preview 20 элементов/страницу с причинами и dry-run
хранилища, безопасные удаления. Меню пользователя — настоящий аккордеон в
`NavigationDrawer`, кнопки/ARIA, ID query, reader/back/focus, прежние персональные
категории, избранное, поиск и скрытые общие категории.

## Воспроизведение и ручная приёмка

Эмуляторы запускаются только с demo project, без production credentials. CLI:
`npx -y firebase-tools@latest emulators:exec --only auth,firestore --project demo-rules "node scripts/smoke-prayer-categories.mjs"`.
Для установленного Firebase CLI есть `npm run smoke:prayer-categories`.
Chromium: `BENCHMARK_BROWSER_PATH=/path/to/chromium`, по умолчанию `/usr/bin/chromium`.
Полная проверка прежних priest rules/UI: `npm run test:priest:rules`.
Тестовый Vite transform направляет Firebase SDK в локальный demo emulator;
страница браузера блокирует все внешние HTTP-запросы. Тестовая роль UI задаётся
harness; реальное право чтения/записи отдельно проверяется emulator Rules матрицей.

1. Администратор открывает `/admin/prayer-categories`: раскрыть родителя и два
   уровня детей, свернуть; сравнить direct count и число детей.
2. Найти лист по имени/тегу: родители остаются контекстом; проверить три access
   фильтра, отсутствие результатов, состояния загрузки/ошибки.
3. «Дадаць падкатэгорыю»: правильный родитель заполнен. Создать пустую папку без
   тегов, затем вручную назначить опубликованную молитву. Сохранить, reload:
   ID/порядок/существующая иконка/manual IDs сохранены.
4. В picker найти молитву, выбрать/снять, включить «Толькі выбраныя», отменить:
   исходный выбор сохранён. Повторить и нажать «Гатова», затем сохранить.
   Удалённая ручная связь при совпадающем теге не убирает молитву из preview.
5. Попытаться назначить себя/потомка/несуществующего родителя и повторный ID:
   отклонено. Попытаться удалить родителя с детьми: сначала предложено перенести
   детей; молитвы не удаляются. Удалить последний тег: папка и дети остаются.
6. В локальном demo изменить `priestOnly` у родителя/листа, добавить/снять ручную
   связь: проверить plan, перенос обеих сторон одной транзакцией и версию
   `priestContentControl`; более 400 операций блокируется без записи.
7. Public: открыть меню, Enter/Space раскрывают узел на месте; лист → список →
   привычный reader → Back. Ветки/фокус/scroll восстановлены. «Малітвы гэтай
   катэгорыі» не включает детей; неизвестный query ID не раскрывает данные.
8. Проверить без grant / с grant / admin: public не видит private заголовков даже
   при пересечении категорий; grant видит protected из разрешённого источника.
   Снятие grant не оставляет private в disk cache. Избранное, поиск и личные
   категории работают, скрытый публичный родитель не раскрывает запрещённую ветку.
9. Проверить 320, 375, 768, desktop во всех light/dark/marian темах, picker/preview
   со множеством результатов, keyboard focus и доступность кнопок сохранения.
10. Flutter-команда прогоняет C01–C09 и настоящий старый decoder на новом gzip;
    после этого — отдельное согласование порядка публикации с владельцем.

## Ограничения выпуска

Публичная категория может содержать непрозрачный ID закрытой молитвы; это не
заголовок и не право чтения. Открытие/закрытие затрагивает все перекрёстные связи,
поэтому оценку плана надо проверить перед сохранением. Массовые операции требуют
отдельного snapshot-based плана; автоматической частичной записи нет.

Защищённого статического bundle здесь не существует: актуальный защищённый
канал — Firestore под grant. Контракт и копируемый Flutter handoff находятся в
[prayer-categories-contract.md](../prayer-categories-contract.md).
Ни merge, ни Hosting deploy, ни Firestore apply, ни публикация manifest/bundle
этой работой не выполняются.
