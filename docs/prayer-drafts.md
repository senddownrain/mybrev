# Чарнавікі малітваў: два станы

Калекцыя `prayerDrafts` даступная толькі `admin`, `superadmin` і legacy-адміністратарам праз `isAdmin()`. Звычайны карыстальнік і святар без ролі admin не бачаць чарнавікоў. Чарнавікі фізічна не знаходзяцца ў `prayers`, каб іх не паказалі старыя Flutter-кліенты.

## Станы і рэдагаванне

У адміністрацыйным інтэрфейсе ёсць толькі **Чарнавік** (`draft`) і **Апублікавана** (`published`). Кнопкі: **Захаваць чарнавік** і **Апублікаваць**. Адміністратар можа апублікаваць непасрэдна з чарнавіка; другіх этапаў узгаднення няма.

Старыя запісы са статусамі `needs_review`, `ready_for_publication` або `archived` адлюстроўваюцца як **Чарнавік**. Пры захаванні пераходзяць у `draft`; іх таксама можна адразу апублікаваць. Не патрэбна масавае перапісванне базы.

Палі рэдактара: назва, тэкст, тэгі, доступ для святароў (`priestOnly`) і звычайны тэкст **Крыніца** (`source`). Калі крыніца імпартаваная з кнігі, аўтаматычна падстаўляецца кніга, выданне, старонкі і наяўны `©` з імпарту; адміністратар можа адрэдагаваць поўны тэкст крыніцы.

Сістэма **не патрабуе** `rightsStatus`, `rightsBasis`, `rightsConfirmedBy`, `rightsConfirmedAt` або асобных палёў `copyrightNotices` для публікацыі. Старыя тэхнічныя метаданыя застаюцца ў гістарычных дакументах для сумяшчальнасці, але не ўплываюць на дзеянні адміністратара. Самі аўтарскія пазнакі ў тэксце крыніцы не выдаляюцца.

## Публікацыя і надзейнасць

`src/utils/prayerDraftActions.mjs#publishDraft` і `prayerContentWriter.mjs` выконваюць адну транзакцыю: у `prayers` або `priestProtectedPrayers` запісваецца малітва, павялічваецца версія кантэнту, чарнавік атрымлівае `published`, дадаецца аўдыт. Правілы патрабуюць звязаную публічную малітву з `sourceDraftId`.

- Без назвы, тэксту, хаця б аднаго тэга ці крыніцы публікацыя блакуецца.
- Пры супадзенні назвы патрэбна рашэнне **стварыць новую** ці **замяніць існуючую**; замена захоўвае ID і спасылкі.
- Паўторная публікацыя вяртае той жа ID; канфлікты версій і content lock перарываюць аперацыю без паловы выніку.
- `priestOnly` — выбар аўдыторыі, не стан публікацыі.

## Імпарт і выхад на прылады

Афіцыйныя кнігі могуць ствараць і замяняць малітвы пры правераным `planSha256`; спрэчныя запісы і «Бог Добры» ідуць у закрытыя чарнавікі. `rights.json` не патрабуецца. Абавязковыя тэхнічныя аховы імпарту (backup, праверка адбіткаў, lock, idempotency, rollback) застаюцца.

Пасля абнаўлення `firestore.rules` трэба асобна выканаць `firebase deploy --only firestore:rules`; для Web — Hosting deploy. Flutter атрымлівае абноўлены кантэнт па асобным `npm run content:manifest` → `--apply` (гл. `docs/app-content-distribution.md`).

## Праверкі

`npm run test:drafts`, `npm run test:import`, `node --test tests/prayer-draft-model.test.mjs`, `scripts/smoke-prayer-drafts-ui.mjs`. Ролі `admin` і `superadmin` могуць рэдагаваць і публікаваць; звычайны `admin` не атрымлівае права кіраваць адміністратарамі або доступамі святароў.
