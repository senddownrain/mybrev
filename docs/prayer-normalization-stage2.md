# Нормализация молитвенника: этап 2

Код и инструменты подготовлены для `mybrev-markdown` v1. Production-данные
не изменялись. Свежий разрешённый экспорт 13 октября 2026 года отклонён
Firestore с `Quota exceeded` (code 8); выполнен полный dry-run **имеющегося
локального** снимка от 12 октября. Полнота и актуальность текущего production
не подтверждены. Окончательный план применения должен строиться заново
после восстановления квоты. Подмена источника старой копией с новой датой запрещена.

Основная причина пропусков первого renderer — оформление меток `**С.:**`,
`_Н.:_`, выделение всей/многострочной реплики и фактические обозначения
`Усе:` / `Цэлебрант:`. Новый reader и CodeMirror распознают их через общую
структуру Markdown. Чтение проектирует разметку в памяти, сохраняя исходный
текст, пунктуацию и выделение произносимых слов; массовый rewrite для этого
не нужен. Инициал с именем (`С. Імя:`), цитаты, списки и код не становятся
участниками. Римские заголовки определяются по структуре/контексту, а не
переименовываются в роли. Самостоятельные метки объединяются со следующей
строкой автоматически только в подтверждённом диалоге одного абзаца.

Подлинный локальный фрагмент «Анёл Панскі» найден **в теле сборной молитвы**.
Первый аудит ошибочно ограничился названиями. Здесь `>` — валидные Markdown
blockquotes, не доказанный дефект импорта. Они сохраняются. Обёрнутые метки
сразу после цитат распознаются; произносимые слова и формулы не дописываются.
Обезличенные тестовые формы находятся в `tests/fixtures/prayer-legacy-shapes.json`;
полные исходники, IDs и diff не публикуются. Дополнительный тест реального
локального corpus включается переменной `PRAYER_NORMALIZATION_SNAPSHOT`.

## Категории и доказательства

- **automatic**: кодировка переносов/BOM; однозначные метки/двоеточия;
  удаление обёртки только метки; сохранение выделения тела реплики;
  подтверждённый перенос метки; точный ограниченный словарь отдельных
  указаний (`Усе ўстаюць.`, `Святар кажа:` и т. п.); подтверждённый legacy HTML.
- **assisted**: целые абзацы с более сложным действием, стили HTML,
  самостоятельная метка без достаточного контекста, склеенные реплики с
  повреждённым курсивом. Группы объединяют одинаковые исходные фрагменты,
  а не тысячи обычных курсивов. Каждая группа содержит before/after, diff,
  confidence и точные поля/строки. Изменение видимых служебных `*` и
  предполагаемого курсива явно требует визуальной проверки.
- **manual**: непроверенные алфавиты/инициалы, повреждённые рубрики,
  неподдерживаемые HTML/версии, либо проверка сохранения не прошла.

Обычные повторы литаний, курсив, заголовки, валидные цитаты и пустые
необязательные языковые поля **не считаются ошибками**. Показатели считаются
по документам и текстовым версиям; категории могут пересекаться.
«Уже читается правильно» отличается от «уже канонично записано»: старое
двоеточие умеет читать первый renderer, но canonical rewrite его убирает.

Для automatic сравниваются последовательность всех слов, пунктуация
(кроме двоеточия метки и допустимого whitespace), ссылки, заголовки и число
цитат; проверяются рубрики и повторная нормализация. HTML требует полной
подтверждённой DOM-структуры из поддерживаемых тегов, сохранения visible text
и href/title. Стили, literal HTML в объявленном Markdown и неизвестные теги
не конвертируются молча. Заголовки, названия, права и теги не переписываются.
Mass-документы не попадают в automatic без отдельного доказательства parity;
форме Mass отключена новая нормализация сохранения и MD autofix. Сам Mass
adapter и speakerLabels/roleLabels/rolePolicy не менялись.

## Повторный dry-run и выборочная проверка

```powershell
node scripts/normalize-prayer-legacy.mjs --snapshot backups/<source> --out backups/<unique-private-run>
# Для этой ограниченной проверки использован --source-status quota-blocked.
# После нового успешного экспорта можно указать --source-status fresh-export.

# Только локальная выборка; записи нет:
node scripts/normalize-prayer-legacy.mjs --plan backups/<run>/plan.json --rule speaker-label --id <approved-id> --out backups/<unique-selection>
```

Скрипт никогда не обновляет snapshot самостоятельно. Выходной каталог
должен быть новым и находиться в ignored `backups/`; symlink/junction за его
пределы запрещён. Public `reports/prayer-format-stage2.md` содержит только
агрегаты и hash плана. JSON с содержимым/группами не переносить в `public/`,
отслеживаемые отчёты или PR. `.gitignore` допускает только public Markdown.

Для нового экспорта требуется доступная квота и разрешение владельца.
Используется существующий exporter, только prayers и prayerCategories,
в новом уникальном каталоге (предварительно проверить target и target.tmp):

```powershell
node scripts/export-firestore-snapshot.mjs --output backups/<unique-source> --collection prayers --collection prayerCategories --project-id ibreviaryby --prefer-rest --require-new-output
```

## Применение и восстановление — только после отдельного утверждения

Нужны: свежий snapshot (не старше 24 часов), точный SHA256 локального плана,
утверждённые automatic-правила и при необходимости IDs. План с отметкой
quota-blocked применяться не может. Assisted-группы apply не принимает:
они остаются review-материалом для отдельного решения, а не скрытой добавкой
к выбранным правилам. `--all-automatic` — явный выбор всех automatic-правил.

```powershell
# Не выполнялось в этой задаче:
node scripts/normalize-prayer-legacy.mjs --plan backups/<run>/plan.json --plan-hash <approved-sha256> --rule speaker-label --rule speaker-line-emphasis --journal backups/<unique-apply-journal>.json --apply
```

Проверяется весь исходный документ (включая права/закрытую metadata),
а не только текст. Новый exporter дополнительно сохраняет updateTime каждого
документа; старые копии без него нельзя использовать для production apply.
Это metadata приватного backup, а не новая схема Firestore или app content.
Backup и журнал сохраняются **до** первой записи.
Каждый пакет (по умолчанию 10, максимум 40) повторно проверяет дрейф;
write использует lastUpdateTime. FieldPath обеспечивает запись только
изменённых языковых полей, включая безопасное обращение с ключами.
updatedAt, права и прочие поля не меняются. Post-write verification
сверяет полный ожидаемый документ и все изменённые поля.

Перед commit в журнал записывается inFlight. При неизвестном результате
прерванного пакета повторный запуск сверяет before/after и подтверждает
применённые ID; никогда не пишет поверх третьего состояния документа.
Повторить apply следует с теми же plan hash, правилами, IDs и journal.
Ограничение 24 часа относится к началу новой операции; продолжение уже
подготовленной утверждённой операции опирается на тот же journal и проверку
всех исходных/записанных версий, включая pending документы.
Это не глобальная транзакция: успешные ранние пакеты сохраняются при сбое.

```powershell
# Отдельное разрешение на восстановление; original journal сохраняется:
node scripts/normalize-prayer-legacy.mjs --plan backups/<run>/plan.json --plan-hash <same-approved-sha256> --journal backups/<apply-journal>.json --restore-journal backups/<unique-restore-journal>.json --restore
```

Восстановление охватывает только подтверждённые применённые документы.
Перед ним нужно reconcile inFlight; оно не перезаписывает последующие
редакторские изменения (проверяется записанная версия документа). Before возвращается только в изменённые поля,
в том числе отсутствовавшие format-поля удаляются. Прерванное восстановление
можно продолжить с тем же restore-journal. Журнал должен совпадать с
выборкой approved plan, проверяются hash и lineage.

## Flutter и публикация

Формат базы остаётся v1. Старый Flutter сможет прочесть слова и Markdown,
но удаление wrapper только метки может убрать её прежнюю жирность, пока
мобильный parser не перенесёт контракт 1.1. Поэтому сначала можно выпустить
совместимое чтение в вебе, а массовую запись/доставку согласовать отдельно
с обновлением Flutter. Есть только локальная оценка diff против snapshot,
не проверка текущего published manifest.

Полный dry-run попадает под **MASS CONTENT REBUILD** (более 20 документов
и более 25% коллекции). После утверждённого применения требуется новый
bundle + app release согласно `docs/app-content-distribution.md`.
Не дробить план на waves для обхода порога, не использовать override.
Скрипт не публикует contentManifest и не выполняет deploy. Для отдельных
утверждённых исправлений публикация — сначала `content:manifest` dry-run,
затем `--apply` лишь при SAFE CONTENT PATCH и отдельном разрешении.
