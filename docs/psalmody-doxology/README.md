# Аудит славословия после псалмодии

PR: [Web #210](https://github.com/senddownrain/mybrev/pull/210), [Flutter #72](https://github.com/senddownrain/ibreviarybyapp/pull/72).

Production не изменён. Ни deploy, ни правила безопасности, ни манифест приложения не публиковались. Снимок и ключи не входят в Git. Дата проверки: 07.11.2026.

## Причина

Исходные общие тексты сохраняли принятую в печатной книге экономию повторяющегося окончания. В заупокойном формуляре даже осталось сокращение «Хвала Айцу. Верш Хвала Айцу чытаецца ў канцы ўсіх псальмаў і песняў». Импорт не разворачивал его. `patchs/generate-db-feasts.mjs` переносил HTML без дополнения; `formatPsalmHtml()` только форматирует его и удаляет встроенную повторную антипфону. Поэтому отсутствие перешло в Firestore и Flutter bundle. Старый тест `laudesPs3` проверял наличие строки во всём поле: корректный Пс 150 скрывал пропуск у Пс 146.

Сезонный парсер также заново воспроизводил сокращённый печатный текст. Теперь его `renderPsalm()` разворачивает окончание. При сравнении библейского текста с печатным источником полное добавленное славословие учитывается отдельно: оно не создаёт ложных сезонных различий. Чтения, гимны, респонсории, молитвы и библейские слова не исправляются. Отдельная сверка всех 546 изменённых полей исходников и генерации с Git-базой подтвердила сохранность библейских слов и антипфон: [source-integrity.json](source-integrity.json).

## Исключения и ссылки

* Дан 3, 57–88.56: исключение разрешено только вместе с собственным окончанием «Благаславім Айца і Сына, і Духа Святога…». 341 вхождение в production: 1 Templates, 17 Proper, 323 days. Ни одно не изменено. Дан 3, 52–57 не освобождается от обычного славословия.
* Заклік: 16 фрагментов четырёх псалмов читаются с антипфоной между строфами; полное славословие уже находится в последнем непустом фрагменте каждого псалма. К отдельным строфам ничего не добавляется (№ 125).
* Разделённые псалмы обычных часов проверяются по каждой части (№ 124), а не как строфы Закліку.
* `from-first-week`, `from-day`, `_fieldRules` и ссылочные массивы не считаются псалмами без окончания. Семь дополнительных ссылочных полей («Дадатковая псальмодыя…», в том числе отсылки к Пс 129/131) сохранены как рубрики, без выдуманных текстов. Окончательно собранная псалмодия проверена отдельно.
* Benedictus, Magnificat, Nunc Dimittis уже содержат полное окончание в Web и Flutter; не изменены.
* Апокалиптическая песнь с ответами «Аллелюя» уже содержит обе части славословия: ответы между полустишиями не являются причиной добавлять второе.

## Воспроизведение

```sh
npm run audit:doxologies -- --check
npm run test:doxologies
# Все операции ниже офлайн; snapshot предварительно получен разрешённым чтением.
npm run audit:doxologies -- --snapshot backups/firestore-snapshot --flutter ../ibreviarybyapp
npm run verify:doxologies
# Только локальные источники; второй запуск — 0 изменений:
npm run audit:doxologies -- --write-sources --check
node scripts/liturgy/common-seasons.mjs --write
npm run generate:fixed-feasts
node scripts/liturgy/common-seasons.mjs --check
```

Аудит также отклоняет славословие перед библейским текстом или после повторной антипфоны; общий suffix нескольких альтернатив требует проверки и не дополняется автоматически. Повторный хоровой ответ после окончания песни допускается, если тот же ответ уже есть в её строфах.

Аудит не содержит Firestore-клиента и не поддерживает `--apply`. Для будущей публикации он формирует локальные `reports/doxologies/firestore-commit-request-N.json`. Каждый write содержит только исправленные поля, updateMask и серверное `currentDocument.updateTime` с наносекундами. Пакеты ограничены 400 writes/8 MiB. Проверка SHA-256 и updateTime выполняется также локально; изменение документа после снимка требует нового рассмотрения, а не снятия precondition.

Нет дублирования и горизонтального переполнения, знаки каденции красные. Внешняя сеть браузера заблокирована. Снимки и результаты: `audit-evidence/doxologies/`.
* Финальный аудит исправленного Flutter bundle: 16 049 полей/правил; 0 пропусков. SHA-256 всех 2 598 изменённых полей **точно** совпадает с afterSha256 Firestore dry-run ([flutter-exact-hashes.json](flutter-exact-hashes.json)).
* Flutter SDK отсутствует в рабочем окружении (`flutter devices`: command not found). Dart/widget-тесты, analyze и реальный Flutter Web smoke локально не подтверждены. Их нельзя заменять Web-снимками. Flutter PR должен оставаться draft до прохождения этих проверок; команды и кандидат бандла находятся в сопутствующем PR.

## План публикации — только после отдельного разрешения

1. Проверить оба PR и Flutter CI/визуальный smoke. Не merge/deploy автоматически.
2. До записи перечитать только 295 кандидатов и сравнить их точные updateTime и хеши. При расхождении остановиться; пересчитать и отдельно проверить конфликтующие поля. Сохранить приватный обратный патч для изменяемых полей. Подать подготовленный пакет с preconditions; не выполнять полный импорт feast/database.
3. Выполнить readback только изменённых полей, сверить afterSha256, повторить аудит, 12.11 и 02.11. Правила безопасности не менять.
4. Манифест сейчас отстаёт от live days/Templates; `liturgicalProperTexts` ещё отсутствует в current-манифесте. [publication-dry-run.json](publication-dry-run.json) явно фиксирует эти различия. Его diff **от локального live-снимка**, а не окончательный diff от опубликованных hashes.
5. Уже собственный вклад этого исправления даёт **MASS CONTENT REBUILD**: 27.0 MiB хранимых документов приложения; days 277/736. Это больше размера REST-запроса (~5.9 MiB), потому что приложение загружает изменённые документы целиком. Обычный `content:manifest --apply` не подходит; override не разрешён и не выполнен.
6. Следовать `docs/app-content-distribution.md`: после разрешённой записи — свежий снимок, `content:app-release` с `--compare-live`, полный бандл, штатный релиз приложения. Ревизии/версию пакета назначает процесс выпуска. Новые коллекции вводить в манифест только после релиза с ними. Нужное действие с манифестом согласовать отдельно, не обходя MASS CONTENT REBUILD.
7. Web: после публикации данных штатно обновить `CONTENT_REVISION` и выпустить Web по отдельному разрешению, чтобы устаревший persistent cache перечитался. Runtime-добавления к текстам нет. Flutter применяет новый baseline штатным ContentStore: старый overlay уступает более новому бандлу, повторная синхронизация не добавляет HTML повторно.
