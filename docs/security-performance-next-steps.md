# Задача: следующий этап безопасности и производительности MyBrev PWA

## Цель

Сделать серверную модель доступа воспроизводимой, измерить и сократить холодную загрузку публичных маршрутов, а также закрыть оставшиеся технические риски после UX/UI/performance-аудита.

## 1. Зафиксировать и проверить Firestore Security Rules — P0

- Получить фактически развёрнутые production rules из проекта `ibreviaryby`.
- Не заменять их предположительной конфигурацией до сравнения с production.
- Добавить `firestore.rules` в репозиторий и подключить файл в `firebase.json`.
- Реализовать модель deny-by-default:
  - публичное чтение только опубликованного контента;
  - запись только для администратора, подтверждённого серверными правилами;
  - клиент не может создавать или изменять `admins/{uid}` для самого себя;
  - неизвестные коллекции закрыты.
- Добавить emulator-тесты для гостя, авторизованного пользователя и администратора.
- Проверить все используемые коллекции: `days`, `fixedDays`, `readings`, `invitatoriums`, `completoriums`, `prayers`, `prayerCategories`, `songs`, `yearOptions`, `bible_bel`, `bible_ru`, `admins`.

### Ограничения

- Сначала использовать локальный snapshot из `backups/firestore-snapshot/manifest.json`.
- Не обновлять snapshot и не запускать live-аудит Firestore без явного подтверждения доступной квоты.
- Деплой rules выполнять отдельно от миграций данных, после успешных emulator-тестов.

## 2. Профилировать холодную загрузку — P1

- Использовать `npm run benchmark:routes`, минимум пять прогонов на маршрут.
- Зафиксировать количество, длительность и размер Firestore-запросов при первом открытии:
  - главной;
  - чтений;
  - литургического часа;
  - текста Мессы.
- Отделить время загрузки Firebase/сети от Vue rendering и заполнения IndexedDB.
- Оптимизировать только подтверждённые узкие места: объединение запросов, дедупликацию, предварительный локальный индекс или уменьшение объёма документов.
- Повторить cold/warm benchmark и приложить исходные JSON-результаты.

## 3. Разобрать зависимости — P1

- Выполнить полный `npm audit` и классифицировать advisories по production/dev dependency и достижимости.
- Обновить прямые зависимости без изменения публичного поведения приложения.
- Для несовместимых major-обновлений оформить отдельные задачи с оценкой миграции.
- После обновлений выполнить тесты, production-сборку и браузерный smoke-тест.

## 4. Добавить стабильный маршрут «сегодня / текущий час» — P2

- Спроектировать маршрут, который сам разрешает текущую дату, литургический день и нужный час.
- Не дублировать календарную бизнес-логику в service worker или manifest.
- После появления стабильного маршрута добавить PWA shortcuts для основных сценариев чтения.
- Проверить переходы при смене даты, часового пояса и в офлайн-режиме.

## 5. Усилить CI-проверки — P2

- Добавить отдельную команду typecheck для Vue/JavaScript-конфигурации проекта.
- Запускать в CI: lint без автоисправлений, 242+ модульных теста, production build и проверку Firebase-конфигурации.
- Добавить browser smoke как отдельный release-check с локальным production preview.

## Критерии готовности

- Firestore rules хранятся в Git, подключены в `firebase.json` и покрыты emulator-тестами.
- Гость не может записывать данные; обычный пользователь не может повысить себе права; администратор сохраняет необходимые редакторские операции.
- Для cold и warm загрузки опубликованы воспроизводимые замеры до и после изменений.
- Critical/high advisories либо устранены, либо документированы с обоснованием и отдельной задачей.
- Все модульные тесты, lint, typecheck, production build и browser smoke проходят.
- Деплой rules, hosting и любые миграции данных выполняются независимыми, откатываемыми этапами.
