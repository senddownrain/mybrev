# Спеўнік: Word для камісіі і бяспечная праверка

Экспарт і праверка працуюць **цалкам лакальна**. Яны не ініцыялізуюць Firebase,
не чытаюць live Firestore, не публікуюць manifest, не змяняюць seed або Flutter.
Каманды прымянення няма; `--apply` адхіляецца як невядомы аргумент.

## Усталяванне і паўторны экспарт

Патрэбны Node (як для асноўнага праекта) і Python 3.9+.
Python абраны таму, што `python-docx` стварае рэдагавальны Word, а `lxml`
дае незалежнае чытанне OOXML з праверкай ID, закладак і Track Changes.
Node-адаптар паўторна выкарыстоўвае `TAGS_LIST` і існуючы правераны snapshot-reader.
У патрабаваннях няма воблачных сэрвісаў або дадатковага UI.

```bash
python3 -m venv .venv-song-review
. .venv-song-review/bin/activate
python3 -m pip install -r scripts/song-review/requirements.txt

# Дакладна зададзены offline-каталог; не выкарыстоўвае аўтаматычнае зліццё:
npm run songs:review:export -- --source src/data/songs.json --out out/songbook-review/seed-v1

# Read-only: правераны лакальны Firestore snapshot, songs паверх seed па ID:
npm run songs:review:export -- --source backups/firestore-snapshot --out out/songbook-review/snapshot-v1

# Fallback без --source: толькі ўбудаваны seed, непацверджаная паўната:
npm run songs:review:export

npm run songs:review:check -- \
  --input path/to/reviewed.docx \
  --baseline out/songbook-review/seed-v1/songs_review_baseline.json \
  --current-source src/data/songs.json \
  --out out/songbook-review/checked-v1

npm run songs:review:test
```

Windows: актывацыя venv — `.venv-song-review\Scripts\activate`;
калі каманда называецца `python`, запускайце `python scripts/song-review/review.py export|check ...`
і `python -m unittest discover -s tests -p song_review_test.py -v`.
Без доступу да PyPI ўсталюйце залежнасці з лакальнага даверанага wheel-cache.

`--source FILE` прымае JSON-масіў аб'ектаў са стабільнымі радковымі ID;
гэта поўная замена лакальнага ўваходу. Ён пазначаецца `source=seed-only`,
бо не пацвярджае стан Firestore. `--source DIRECTORY` чытае толькі калекцыю
`songs` праз `scripts/lib/firestore-snapshot.mjs`: схема, checksum і колькасць
правяраюцца існуючым reader. Няма `songs` — памылка, не маўклівы fallback.
`--seed FILE` задае іншы seed для merge. Не прапускайце яго пры наступнай
праверцы нестандартнага seed. Іншыя калекцыі snapshot не чытаюцца і не экспартуюцца.

Без `--current-source` checker паўторна чытае шлях source з baseline;
для snapshot выкарыстоўвае актуальны seed гэтага checkout. Калі шлях недаступны,
праверка блакіруецца; перадайце свежы лакальны ўваход відавочна.
Змяненне любога поля зыходнай песні (уключна з timestamps), новы або зніклы ID
пасля экспарту — канфлікт. Непарушаны стары snapshot пацвярджае толькі
адсутнасць дрэйфу ў гэтым snapshot, не ў production. Перад будучым прымяненнем
уладальнік павінен даць актуальны snapshot і асобна дазволіць патрэбныя live reads.

Не перазапісвайце baseline: экспарт у каталог з існуючым Word/baseline адхіляецца.
Заўсёды выбірайце новую версію `--out`. Артэфакты і scratch ігнаруюцца Git.

## Што перадаваць камісіі

У каталогу экспарту:

| Файл | Прызначэнне |
| --- | --- |
| `Speunik_dlia_kamisii.docx` | Галоўны рэдагавальны дакумент |
| `README_dlia_kamisii.md` | Кароткія правілы, таксама ў пачатку Word |
| `songs_review_baseline.json` | Уладальніку: дакладныя ўваходныя аб'екты, дадатковыя палі, хэшы, крыніца і версія |
| `export_report.json` | Колькасці, overrides, пропускі, дублікаты ID, невядомыя катэгорыі, падазроныя радкі |
| `potential_duplicates.csv` | Аднолькавыя назвы з рознымі ID: толькі кандыдаты для ручнога абмеркавання |

У Word: A4, Times New Roman 12, нумары старонак, змест раздзелаў і
загалоўкі песняў. Убудаваны спіс раздзелаў бачны адразу; дынамічны TOC можна
абнавіць Ctrl+A → F9. Асноўная катэгорыя — першая вядомая катэгорыя ў `tag`;
раздзелы ідуць у парадку `TAGS_LIST`, далей беларускі алфавіт, ID для развязання
роўных назваў. Кожная песня паказваецца адзін раз; усе катэгорыі бачныя ў картцы.
Невядомыя катэгорыі паказваюцца, пазначаюцца ў справаздачы і захоўваюцца, калі
не рэдагаваліся. Дадаванне невядомай катэгорыі падчас рэвізіі блакіруецца.

`SONG_ID` мае незалежную закладку, другая закладка звязвае табліцу радкоў з ID.
Дадатковыя captions могуць знікнуць у LibreOffice; асноўныя закладкі абавязковыя.
Не рэдагуйце ID, подпісы палёў, загалоўкі калон і структуру метададзеных.
Катэгорыі/тэгі рэдагуюцца па адным абзацы на пункт, без JSON або праграмавання.
Новыя строфы — новыя радкі табліцы. Не злівайце ячэйкі.

LF/CRLF/CR у Word адлюстроўваюцца як аднолькавыя межы радкоў.
Калі змест не змяніўся, checker вяртае зыходны радок з дакладнымі line endings,
прысутнасцю/адсутнасцю палёў і канчатковымі пустымі радкамі. Новыя тэкставыя
змены выкарыстоўваюць LF. Кароткая калонка дапаўняецца пустымі ячэйкамі толькі
для паказу; вядомы export-padding не лічыцца новым зместам. Пры даданні радкоў
параўноўвайце абедзве калонкі: пустыя новыя радкі таксама ўваходзяць у diff.
Некаторыя існуючыя text/chord маюць розную колькасць радкоў: гэта папярэджанне,
а не аўтаматычная «выпраўленая» страта прыпеваў. Неадназначныя шматрадковыя
ячэйкі з рознай колькасцю радкоў у калонках блакіруюцца.

LibreOffice пры захаванні абразае прабелы/табуляцыю ў канцы абзаца.
Checker лічыць толькі гэтыя канчатковыя ASCII-прабелы/табуляцыю афармленнем
і аднаўляе іх з baseline на нязмененых радках. Унутраныя прабелы,
адступы, беларускія літары і ўсе межы радкоў застаюцца значнымі.
Гэта дазваляе атрымаць дакладны зыходны радок пры нулявым round-trip.

## Вынік dry-run

`review_diff.json` змяшчае рашэнне/заўвагі па кожным распазнаным ID,
старыя/новыя значэнні змененых палёў, лічыльнікі рашэнняў/палёў, змены колькасці
радкоў, source conflicts і каментарыі. `review_summary.md` — кароткая чалавечая
справаздача. `applicable` заўсёды false: гэтая праграма нічога не ўжывае.

Exit 0: структурная праверка пройдзена, але **гэта не approval**.
Exit 2: памылка, канфлікт або рашэнне `АБМЕРКАВАЦЬ`.
ID адсутнічае/зменены/паўтараецца, страта карткі, незнаёмы статус,
неадназначныя палі, злітыя ячэйкі, невядомыя аб'екты ў картцы,
незавершаныя Track Changes у любой Word XML-частцы — блакіроўка.
Каментарыі запісваюцца ў справаздачу, але не мяняюць рашэнні і тэкст.
Для імпарту патрэбна асобная чыстая фінальная копія з прынятымі/адхіленымі
адсочванымі праўкамі. Выдаленая картка ніколі не азначае выключэнне.
Hash baseline правярае цэласнасць; гэта не крыптаграфічны подпіс камісіі.

## Даследаваная архітэктура і межы паўнаты

Web, `src/services/songService.js`: seed → частковае зліццё палёў Firestore
па document ID → `publicContentCache` з `SONGS_CACHE_VERSION=4`.
`src/stores/songs.js` пачынае з cache або seed. Таму seed сам па сабе не даказвае
актуальную поўную калекцыю. Рэдактар `src/views/admin/SongEditor.vue` захоўвае
`title`, `text`, `chord`, `tag`, `tags`, `source`; Firestore таксама мае
`createdAt`, `updatedAt`. Тэхнічны ID не залежыць ад назвы і парадкавага нумара.
Baseline захоўвае ўсе іншыя палі, нават калі яны не рэдагуюцца ў Word.

На 2026-11-03 у правераным main: **447 у seed**, 7 палёў у кожнай песні:
`id/title/text/chord/tag/tags/source`. Лакальнага `backups/firestore-snapshot/manifest.json`
у сесіі няма. Live Firestore не чытаўся. Экспарт пазначаны:
**«ЭТО НЕ ПОДТВЕРЖДЁННАЯ ПОЛНАЯ ВЕРСИЯ ДЛЯ КОМИССИИ»**.
Для пацверджання патрэбны давераны актуальны snapshot калекцыі songs і згода
ўладальніка з датай/складам корпуса. Snapshot можна атрымаць асобна пасля
дазволу на выдатак квоты; гэты workflow яго аўтаматычна не абнаўляе.

Звязаны Flutter правераны read-only праз GitHub:
`docs/songbook.md`, `lib/models/song.dart`, `lib/services/song_repository.dart`,
`lib/content/content_store.dart`, `assets/content/manifest.json` і сам
`assets/content/songs.json.gz`. Manifest: songs 447, contentVersion 1791877294111,
contentDate 2026-10-13T07:41:34.111Z, digest `9752aef2fd846b49`.
Дэкадаваны bundle мае тыя ж 447 ID і ўсе шэсць рэдагуемых палёў, што і Web seed.
`assets/songs_seed.json` у актуальным main вяртае 404, хоць згадваецца ў docs;
рэальны `SongRepository.loadSeed()` чытае `ContentStore`, а не гэты стары файл.
Flutter не змяняўся. Bundle на сваю дату не даказвае стан live Firestore сёння.

## Будучае прымяненне — толькі праект, не выканана

1. Зафіксаваць фінальны Word, baseline, diff, усе рашэнні і спіс выключэнняў;
   уладальнік асобна зацвярджае дакладны hash diff і ID выключэнняў. Сфарміраваць
   версійны кананічны JSON, склад/хэш поўнага зацвярджанага зборніка і кароткую
   запіску: колькасці, катэгорыі, прынцыпы адбору, вынікі рэвізіі. Толькі тады PDF.
2. У асобнай ветцы/PR стварыць асобную каманду прымянення з відавочным `--apply`
   і праверкай approval/hash. Перад запісам пераправерыць актуальныя hash/updateTime
   кожнага мэтавага дакумента (optimistic concurrency), спыніцца пры дрэйфе.
   Захаваць backup, план rollback і вынік кожнай аперацыі для бяспечнага паўтору.
   Дазваляць змяненні толькі `songs`; не закранаць богаслужэнні і іншыя калекцыі.
3. Спачатку ўкараніць тэстуемыя exclusions/tombstones, затым выключаць песні.
   Прапановa: стабільны `excluded: true` у song-докуменце, з захаваннем тэксту,
   ID і праверачнай metadata; цэнтральны кананічны спіс ID для кантролю рэлізаў.
   Фільтрацыя **пасля** merge seed+Firestore і перад cache/UI ў Web; падняць cache
   version і праверыць абнаўленне старога cache. Простае выдаленне Firestore
   вяртае seed, таму ніякіх выдаленняў па змаўчанні. Невядомыя раней палеткі
   павінны ігнаравацца старымі кліентамі; іх выключэнні гарантаваны толькі пасля
   адпаведнага выпуску з фільтрам. Патрэбна асобная сумяшчальная міграцыя.
4. Flutter: дадаць падтрымку таго ж excluded-маркера ў model/repository і
   фільтраваць **пасля** любых seed/cache/overlay merge. Не мяняць ID і не чысціць
   favoriteSongIds: выключаны ID можна паказаць як недаступны, вяртанне песні
   захоўвае абранае. Новы bundle павінен несці tombstones або canonical exclusions.
   Праверыць offline, абнаўленне старой версіі, ачыстку cache, адкат і вяртанне песні.
5. ContentStore ужо падтрымлівае overlay tombstone `x: true`; `planUpdate` робіць
   яго пры выдаленні bundled дакумента. Але `_reconcileWithBaseline` выдаляе
   стары overlay пры новым bundle: калі новы bundle яшчэ ўтрымлівае выключаную
   песню, яна вернецца. Таму canonical bundle і exclusions павінны адпавядаць
   адной зацверджанай версіі; адзін overlay-delete праблему цалкам не вырашае.
6. Спачатку праверыць увесь зацверджаны корпус, пасля рыхтаваць Flutter delivery.
   Web seed, Firestore і bundle павінны несці адзін склад і версію выключэнняў.
   `npm run content:manifest` толькі пасля асобнага дазволу: сёння яго скрыпт
   можа рабіць live reads. Парогі: >300 дакументаў, >5 MB або >25% калекцыі
   і >20 змяненняў/выдаленняў → MASS CONTENT REBUILD. Для сотняў рэвізій
   чакаецца новы кананічны bundle і рэліз прыкладання, без абыходу парогаў.
   Новыя schema/collection патрабуюць узгодненага выпуску кліентаў да manifest.
   Дэталі — `docs/app-content-distribution.md`; нічога не публікуецца аўтаматычна.

## Праверка Word уручную

Аўтаматычна правераны нулявы diff усіх 447 песняў да і пасля перазахавання
праз LibreOffice. Візуальна правераны PNG з Writer і HTML-прэв'ю для
`САМ НА САМ` (кароткая), `СВЯТЫ` (доўгая) і `У любові страху няма`
(тэкставая паметка `Проігрыш` у chord). У актуальным seed эврыстыка знаходзіць
адну песню са словам з трох і больш кірылічных літар у chord; поўны прыпеў
у legacy-калонцы дадаткова пакрыты сінтэтычным тэстам, а не прыдуманай
зменай рэальных тэкстаў. Microsoft Word у гэтай сесіі не запускаўся;
пераносы старонак і абнаўленне TOC у канкрэтнай версіі Word праверце ўручную.

1. Адкрыць кароткую і доўгую песню: назва, катэгорыі, нумар і SONG_ID;
   пагартаць перанос табліцы, паўтор загалоўкаў, нумары старонак і змест.
2. Адкрыць песню з беларускімі словамі прыпеву ў chord: праверыць абедзве
   калонкі, `ў/і/ё`, дыякрытыку, пустыя радкі і канец апошняй страфы.
3. У копіі змяніць назву і паставіць ВЫКЛЮЧЫЦЬ, захаваць DOCX, запусціць check:
   адзін ID, толькі title у fields, рашэнне ВЫКЛЮЧЫЦЬ, без запісу ў базу.
